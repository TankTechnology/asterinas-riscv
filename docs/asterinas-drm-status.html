Asterinas DRM 进展

这套 DRM 现在到哪一步、它相对一个「现代 DRM」处在什么位置、以及它和 Linux 的 DRM 是什么关系。 所有结论都标了证据档位 —— 已验证 部分 缺失。

一句话：DRM 的「传统 KMS + GEM + render node」这一档是完整的，足以让未经修改的 Linux 用户态跑起来；但「现代 GPU 驱动」那一档 —— 原子提交、显式同步、调度器、显存管理 —— 还差得远。

而且最大的空白不在 DRM 子系统本身：我们没有真正驱动任何一块真实的显示硬件。 virtio-gpu 是虚拟设备，板子上用的是固件交接的 framebuffer。物理板子上 /dev/dri/card0 从未被打开过 —— 板子今天能跑的桌面走的是 Xorg fbdev。

关键判断：我们处在「足以让未经修改的 Linux 用户态跑起来」这一档 —— 这不是小事，因为这意味着 ioctl 编号、结构体布局、方向位必须和 Linux 逐位一致。

但驱动那一档是空的：Asterinas 目前不能驱动任何一块真实的显示硬件。 这才是「现代 DRM 程度」里最大的那块空白，而不是缺哪个 ioctl。

四、Linux 里有 DRM 吗

有 —— 而且 DRM 本来就是 Linux 的东西。我们不是在发明一个子系统，是在从零重新实现 Linux 的一个子系统 ABI。

先消歧义，因为这个词有两义：

DRM = Direct Rendering Manager ← 我们说的、Linux 里有的、这个
DRM = Digital Rights Management（数字版权管理）← 完全无关的另一件事

Direct Rendering Manager 的脉络

~1999
引入 为 XFree86 4.0 的 DRI 而生，解决多进程直接访问 GPU 的问题。最初只是 ioctl 的一层仲裁。
2008
GEM — Graphics Execution Manager 统一的内存管理，取代之前的 buffer object。
2009
KMS — Kernel Mode Setting 把模式设置从 X server 收进内核。这是为什么今天开机能看到文字控制台、能无缝切换 VT。
2014–15
Atomic modesetting 模式设置变成事务性的、可测试的提交。
之后
PRIME / DMA-BUF · render node · syncobj · drm_sched 跨设备缓冲共享、无 master 的计算节点、显式同步、GPU 调度。

和我们是什么关系

今天的 Linux DRM 包含几十个驱动（i915、amdgpu、nouveau、msm、virtio-gpu、vkms、simpledrm……）、 上百个文件。上游的 libdrm、Mesa、Xorg、Wayland 全部通过这套 uapi 说话。

我们的做法是：Asterinas 有自己的内核，所以需要自己的 DRM；但照着 Linux 的 uapi 实现， 所以 Linux 那些未经修改的用户态程序能直接用。这正是 Debian 的 Xorg 和 Mesa 能在 Asterinas 上跑起来的原因， 也是为什么我们反复拿「libdrm / Mesa 的行为」当作正确性判据。

代价是：编号、结构体布局、方向位错一位都不行。这个项目里被抓出来的若干缺陷 —— GEM_OPEN 的方向位被声明成 RM_MAP、驱动名被截断成 virtio_gp、若干结构体尺寸不符 —— 都是出在这一层。项目里有一个专门的 uapi 契约测试把全部 ioctl 钉住，原因就在这里。
