# 补齐 `SOL_IPV6` 的 `IPV6_V6ONLY`：失败用例 → 最小实现 → 三层验证

日期：2026-10-27
内核基线：`972f6ae20`
任务书：`/tmp/tp/SOL_IPV6.md`

## 0. 结论

- 改前：`setsockopt` / `getsockopt(IPPROTO_IPV6, IPV6_V6ONLY)` 都返回
  **`EOPNOTSUPP(95)`**（`new_raw_socket_option` 没有 `SOL_IPV6` 分支）。
- 改后：set 成功、读回值正确（设为 1 读回 1，新建 socket 默认 0），
  v4 socket 上设 `SOL_IPV6` 返回 **`ENOPROTOOPT(92)`**，v4 的 `SOL_SOCKET` 对照不变。
- **行为说明（重要）**：这套网络栈是**单栈**实现（一个 socket 固定一个地址族，
  且不支持 IPv4-mapped IPv6）。因此 `IPV6_V6ONLY` 目前**只保存标志、可读写**，
  **不改变** socket 接受哪些包——v6 socket 本来就是 v6-only。
  这与 Linux 的默认值（0，双栈）在**语义上不一致**，但因为没有双栈路径，
  实际可观察行为相同。**未实现双栈**。
- `IPV6_CHECKSUM` 等其他 `SOL_IPV6` 选项一律返回 `ENOPROTOOPT`（明确记录，不静默接受）。

## 3. 任务 C：验证

### 3.1 C1：失败用例改后

```
V6S SET v6only rc=0 errno=0 (Success)
V6S GET v6only rc=0 errno=0 (Success) value=1
V6S DEFAULT v6only rc=0 errno=0 (Success) value=0
V6S CTRL v4_reuseaddr rc=0 errno=0 (Success)
V6S V4_SOL6 rc=-1 errno=92 (Protocol not available)
V6S RESULT v6only_set PASS
V6S RESULT v6only_get PASS
V6S RESULT v6only_default0 PASS
V6S RESULT v4_ctrl PASS
V6S RESULT v4_sol6_enoprotoopt PASS
V6S RESULT all PASS
```

脚本退出码 `check_rc=0`。**改前 FAIL → 改后 PASS**，且 v4 socket 上设 SOL_IPV6
得到 `ENOPROTOOPT(92)`（不是误接受），v4 对照不变。

### 3.2 C2：`iperf3 -s -6` 与 v4 对照

同一新内核、同一镜像，`iperf3 -s -1 -6` 起服务端，客户端连 `::1`：

```
C2 v6_server: iperf3: getsockopt - Protocol not available ... Server listening on 5201 (test #1)
C2 v6_client: Connecting to host ::1, port 5201
              [  5]   0.00-1.00   sec  1.09 GBytes  9.35 Gbits/sec  32767  sender
C2 v4_server: ... Server listening on 5201 (test #1)
C2 v4_client: [  5]   0.00-1.00   sec  1.07 GBytes  9.14 Gbits/sec  32767  sender
```

**v6 监听起来了并完成一次 `::1` 传输**；v4 对照同量级。
`srv4/srv6` 开头那条 `getsockopt - Protocol not available` 在 v4/v6 都会出现，
是 iperf3 探测另一个未实现的选项（非致命，未改 iperf3）。

### 3.4 任务 D：`dig @::1` 重测（判别结论）

```
改前: ;; UDP setup with ::1#18222(::1) ... failed: address family not supported.
改后: ;; UDP setup with ::1#18222(::1) ... failed: invalid protocol.
```

**错误变了**：dig 越过了 `IPV6_V6ONLY` 这一关，撞在**下一个未实现的 SOL_IPV6 选项**
上（`ENOPROTOOPT`，BIND 报成 "invalid protocol"）。因此上一轮矩阵里
"`dig` 的失败是 AI_ADDRCONFIG 还是 SOL_IPV6"的判别结果是：**是 SOL_IPV6**，
不是 AI_ADDRCONFIG。dig 仍未通过，剩下的缺口需要再补选项（本轮不修，见矩阵文档）。

### 3.3 C3：7 域矩阵

第一次运行：七个域的 `DAILY_*` 行在串口上**全部为 ok**，`DAILY_DONE=ok`，
`panic=0`、`allocation failed=0`；但 gate 自身报 `FAIL (no result for: AUDIO)`。
原因是内核的 `number of negative dentries has reached N` 告警洪水把结果行挤在同一行：

```
[806.600] WARN : [DAILY_AUDIO=ok aplay-hw:0,0
```

`DAILY_AUDIO=ok` 被 WARN 前缀与 ANSI 转义交织，解析器没匹配到。这是**串口交织/
脚手架问题**，不是内核失败（该告警与本次改动无关，是 dentry 缓存压力下的既有日志）。

重跑（同一内核、同一镜像）结果：**全绿**。

```
DESKTOP ok  APP ok  APT ok  CLIPBOARD ok  AUDIO ok  USB ok  SUSPEND ok
DAILY_DONE=ok   panic=0   allocation failed=0
```

（`INPUT_METHOD=fail` 是 7 域之外的既有缺口。）v4 的 sockopt 行为在同轮矩阵与 C1 的
`v4_ctrl` 中均未变化；`V4_SOL6` 由改前的 `EOPNOTSUPP(95)` 变为 `ENOPROTOOPT(92)`，
符合 Linux（不误接受）。
