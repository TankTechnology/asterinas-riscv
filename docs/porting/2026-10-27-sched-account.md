# 调度侧五段计时：S5（时钟 tick）最大，但自证仍不通过——而且 stime 基准本身可疑

日期：2026-10-26
内核基线：`a966812e2`
本轮：加五段计时（RAII，热点只做 rdtsc + 原子加）→ 测 → **已 revert**

## 0. 结论

1. 五段（热轮，8 s 窗口）：**S1 调度决策 2.1 ms、S2 状态保存 0.77 ms、S3 唤醒 5.1 ms、
   S4 IPI 发送 2.6 ms、S5 时钟 tick 125.4 ms**，合计 **135.9 ms**（run3 145.4 ms）。
   **最大项是 S5（时钟 tick），占 92 %**，单次约 **3.95 µs**。
2. **自证不通过**：要求「五段合计 ≈ 1.05 s（±35 %）」，实测 136 ms ⇒ 13 %。
   按纪律**没有进任务 B**。
3. **但基准本身有问题**：这些计数器是**全系统**口径，而 1.05 s 来自**单个进程**的 stime。
   更要紧的是，上一轮（`d170e71a4`）已经记录过 stime 不可信的证据——
   「7.5 s 墙钟里 54.8 s 内核时间」在 4 vCPU 上不可能成立。
   ⇒ 「84 % 内核时间未归因」这个结论**依赖一个未经验证的计时基准**。
   下一步应先校准 `/proc/<pid>/stat` 的 utime/stime（HZ、单位、是否重复计入多线程），
   再谈"谁吃掉了内核时间"。

## 2. 一个必须记录的测量陷阱（SC1 → SC2）

第一版把 S2 的 RAII guard 放在 `switch_to_task` 整个函数上，三轮结果都是
**8 427 788 776 ns（8.43 s），三轮完全相同**——因为 guard 活在被切出任务的栈上，
`Drop` 发生在**被重新调度回来之后**，测到的是「被换出的整段时间」而不是切换本身。
改成只计 `before_switching_to` 后才得到 0.77 ms 的合理值。

**教训**：任何跨越上下文切换的 RAII 计时都是错的；只能计切换前的保存段和切换后的恢复段。

## 3. 自证与它的基准问题

| 项 | 数值 | 相对 stime（1.40 s） |
|---|---|---|
| 五段合计 | 135.9 ms | 9.7 % |
| syscall 合计（上一轮同法） | 147.8 ms | 10.6 % |
| 缺页合计（上一轮） | 61.3 ms | 4.4 % |
| **三者相加** | **345 ms** | **24.6 %** |

要求是「≈1.05 s ±35 %」，差得远。但要注意口径：

- 五段/syscall/缺页计数器都是**全系统累计**（所有 CPU、所有进程）；
- stime 是**主进程一个进程**的内核时间。

全系统累计 345 ms **小于**单进程 stime 1.40 s 是自相矛盾的——只可能是 stime 被高估。
这与 `d170e71a4` 记录的「54.8 s / 7.5 s」异常一致。

**因此下一步不是继续找"第四个桶"，而是先校准 stime**：
1. 查 `/proc/<pid>/stat` 的 utime/stime 计算（`thread/mod.rs` 的统计点、HZ、多线程是否重复累加）；
2. 用一个已知工作量的微基准（例如纯用户态忙等 1 s）校准 utime 是否准确。

## 4. 若基准校准后 S5 仍是最大项（留给下一轮的预案）

S5 单次 3.95 µs、1000 Hz/CPU。可选方向（**本轮未做**）：
- 降 tick 频率（1000 → 250/500 Hz）：S5 直接按比例下降，但要评估时间精度与调度时延；
- 精简 tick 回调链（`call_timer_callback_functions` 里逐个回调的开销）；
- 空闲 CPU 上关闭 tick（tickless idle）。
