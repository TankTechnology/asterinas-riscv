# L4 `coreutils`：`TEST_MKNODAT` 证据核查与 root 构建修复

日期：2026-10-25　仓库 HEAD：`517bf3dab`（修复前）
L4 基线内核：`66004cd683dd451b`（`AT_EXECFN` 修复后重建）

## 结论摘要

- **任务假设不成立：不是 mknodat 缺失或行为不符。**
  - `x86_64` 的活树 syscall 表**已注册** `mknodat`（259），实现支持
    `NamedPipe`；`mknod`（133）也委托给 `sys_mknodat(AT_FDCWD, …)`。
  - configure 日志里 `checking for mknodat... yes`、`checking for
    mkfifoat... yes` 均通过；失败点不是它们。
- **真实报错**：gnulib 的
  “whether mknod can create fifo without root privileges” 测试程序在
  `geteuid() == 0` 时**直接 `return 99`**，`mknod()` 根本没被调用；
  configure 随即报
  `you should not run configure as root (set FORCE_UNSAFE_CONFIGURE=1 …)`。
- **根因**：L4 在 guest 内以 **root** 构建；Debian 官方构建使用非 root
  用户，因此上游从不会触发该保护。**这是环境问题（B），不是内核 syscall
  问题。**
- **修法**：在 L4 探针的 `dpkg-buildpackage` 环境里设置
  `FORCE_UNSAFE_CONFIGURE=1`（一行，测试环境修复；**内核代码零改动**）。
- **L4 结果**：**3 包 3 ok / 0 fail —— L4 = 3/3**。`coreutils` 首次通过
  （575.99 s，1 次尝试，产出 `coreutils` 与 `coreutils-dbgsym` 两个
  `.deb`）；`hello`、`python3-minimal` 保持通过。

## 1. 取证：configure 的真实报错

来源：guest `/var/tmp/dpkg-logs/pkg2-build.log`（第二次 L4 重跑，
configure 9.7；归档见
`docs/porting/evidence/2026-10-25-l4-mknodat/configure-root-guard.txt`）。

```
checking for mknodat... yes
checking for mkfifoat... yes
checking whether mknod can create fifo without root privileges...
configure: error: in '/tmp/dpkg-build/pkg2/coreutils-9.7':
configure: error: you should not run configure as root
  (set FORCE_UNSAFE_CONFIGURE=1 in environment to bypass this check)
```

config.log 里能看到测试程序本身与它的退出码：

```
configure:65580: ./conftest
configure:65580: $? = 99
configure: program exited with status 99
configure: failed program was:
…
| int
| main (void)
| {
| /* Indeterminate for super-user, assume no. */
|       if (geteuid () == ROOT_UID) return 99;
|       if (mknod ("conftest.fifo", S_IFIFO | 0600, 0)) return 2;
|   ;
|   return 0;
| }
```

`return 99` 表示“超级用户，无法判断”，测试在调用 `mknod()` 之前就退出；
因此它既没有测到 `mknod`，更没有测到 `mknodat`。

### 为什么 DPKGB 的 evidence 行会指向 `GNULIB_TEST_MKNODAT`

`DPKGB pkg=2 evidence=…GNULIB_TEST_MKNODAT_1__configure:_exit_1…` 是探针
的**启发式摘要**：它取错误行之前的最后几条非噪声输出，而 configure 在
失败时打印的 “failed program” 是 `config.h` 片段，恰好以
`#define GNULIB_TEST_MKNODAT 1` 结尾。这行只是失败程序里的一个宏，
**不是被执行的测试**，也不是缺失的 syscall。

## 2. 核对 x86_64 的 syscall 表（活树）

注意：`kernel/src/**` 是**死树**，改动不会生效；活实现位于
`kernel/core/**`（见 `AGENTS.md`）。本轮的检索与结论都针对活树：

```
kernel/core/src/syscall/arch/x86.rs:79:    mknod::{sys_mknod, sys_mknodat},
kernel/core/src/syscall/arch/x86.rs:377:   SYS_MKNODAT = 259  => sys_mknodat(args[..4]);
kernel/core/src/syscall/mknod.rs:17:       pub(super) fn sys_mknodat(…)
kernel/core/src/syscall/mknod.rs:74:       sys_mknodat(AT_FDCWD, …)   // sys_mknod
```

`sys_mknodat` 的模式分支覆盖 `File / CharDevice / BlockDevice /
NamedPipe / Socket`；`NamedPipe` 走 `dir_path.mknod(…, MknodType::NamedPipe)`。
也就是说：**即使 conftest 真的调用 `mknod`/`mknodat`，注册与实现也都存在。**

结论：无需补注册，也不需要改内核。

## 3. 修法（一处，测试环境）

`tools/x86/debian/dpkg_build.sh` 的 build 阶段：

```sh
timeout -k 10 "$(remaining)" env DEBIAN_FRONTEND=noninteractive \
    DEB_BUILD_OPTIONS="nocheck parallel=4" \
    FORCE_UNSAFE_CONFIGURE=1 \
    dpkg-buildpackage -b -us -uc >"$LOGDIR/pkg$index-build.log" 2>&1 </dev/null
```

- 该变量是 GNU coreutils `configure` **自己文档化**的绕过开关，只为跳过
  “以 root 运行”的探测保护，不改变产物内容或优化选项；
- 只影响设置了该保护的包（本门禁里是 coreutils），`hello`/
  `python3-minimal` 不受影响；
- 内核无需重编译（无内核改动），复用 `66004cd6`。
