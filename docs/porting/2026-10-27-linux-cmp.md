# 与 Linux 的调度/时间口径对照：切换次数只差 1.28×，stime 差 133×

日期：2026-10-26
内核基线：`a966812e2`
探针：`/tmp/vb/linuxcmp_probe.sh`（同负载、同 8 s 窗口、**无采样器**），两内核各 3 次

## 0. 两个问题的回答

**(1) stime 是否被高报？** 对照数据强烈指向「是」：
同一负载下 Linux 主进程 stime = **1 tick（约 10 ms）**，Asterinas = **133 ticks（1.33 s）**，
差 **133×**；而两边的上下文切换率只差 **1.28×**（97/s vs 76/s），线程数相同（4），
VmRSS 相同（90 MB），Asterinas 的 minflt 甚至**更少**（4 471 vs 6 038）。
切换率不足以解释 133×，因此**不是"干了更多内核活"，而是计数口径可疑**——
与 `d170e71a4` 记录的「7.5 s 墙钟里 54.8 s 内核时间」一致。

（保留的替代解释：Linux 侧 `pgrep -f` 可能选中了一个早期阶段/较闲的进程。但两边用的是
**同一探针、同一选择规则**，Asterinas 三次都稳定在 131–396 ticks，Linux 三次 1–30 ticks，
差距不是单次噪声。）

**(2) 84 % 未归因能否用切换次数解释？** **不能。**
- 切换率 97/s vs 76/s = **1.28×**，远低于判据里的 3×；
- 即便按 10 µs/次估算，778 次切换也只有约 8 ms，与 1.33 s 相差两个数量级。
⇒ 按任务书判据：**「两者都相近」⇒ 84 % 不在调度**；而且在本轮对照之下，
「84 %」这个数字本身建立在可疑的 stime 上，**应先修口径再谈归因**。

## 1. 腿 1：两内核可测指标表

| 指标 | Linux 来源 | Asterinas 状态 |
|---|---|---|
| utime / stime | `/proc/<pid>/stat` 14/15 | ✅ 有（同字段位置） |
| minflt / majflt | `/proc/<pid>/stat` 10/12 | ✅ 有（`thread.min_flt()/maj_flt()`） |
| 系统级 ctxt | `/proc/stat` 的 `ctxt` | ✅ 有（`thread/stats.rs` 的每 CPU 计数器） |
| 每任务 voluntary / nonvoluntary 切换 | `/proc/<pid>/status` 或 stat 41/42 | ❌ **缺**（stat 未输出这两个字段） |
| CPU migrations | Linux 需 perf/`schedstat` | **NA**（Asterinas 无 perf） |
| RSS / VmSize / Threads | `/proc/<pid>/status` | ✅ 有 |

**关于「缺 per-task 切换计数」**：本轮**没有补**。判据要的「每秒上下文切换次数」用两内核
**都有的**系统级 `ctxt` 快照即可得到（同一 8 s 窗口前后差值），已足够回答 (2)；
补 per-task 版本需要改 ostd 调度器的 park/preempt 路径 + stat 字段，属于额外的内核改动，
在剩余时间内无法连同两内核各 3 次对照一起验证。**如实标注为缺项**。

## 3. 附带发现：VmSize 差 1000 倍

Asterinas 上同一个 Firefox 主进程报告 **466 GB** 虚拟地址空间，Linux 只有 **447 MB**，
而两者 RSS 完全一致（90 MB）。这说明我们的 `vsize` 统计（或地址空间布局）与 Linux 差三个数量级，
会影响任何按 VmSize 做的估算（例如上一轮 fork 的 VmSize 敏感性分析）。
**这一项也应单独核对**（`/proc/<pid>/status` 的 VmSize 来源）。

## 4. 下一步（按证据强度排序）

1. **校准 utime/stime**：`/proc/<pid>/stat` 的 utime/stime 来自
   `prof_clock.user_clock()/kernel_clock().read_jiffies()`（`procfs/pid/task/stat.rs:186-196`）。
   用一个已知工作量的微基准（纯用户态忙等 1 s、纯 syscall 循环各 1 s）在**两内核**上对照 utime/stime，
   即可判定是「计时点重复累加」「单位（tick vs ns）错」还是「多线程重复计入」。
2. **校准 VmSize**（466 GB vs 447 MB）。
3. 以上两项校准之后，再回头判断「未归因的内核时间」是否真实存在。
4. 若要 per-task 的 voluntary/nonvoluntary 拆分，再补 stat 41/42 字段（本轮标 NA）。
