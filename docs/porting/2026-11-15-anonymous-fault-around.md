# 匿名映射 fault-around：实现了、量到了 9×，但**没有上线**（2026-11-15）

> 结论先写：批量装页在微基准上把顺序触摸从 1.00 次/页降到 0.06 次/页、总时间 9 倍，
> 但在板子上让 Firefox 进入**缺页风暴**（17.7 万 → 466 万次，30k/s，RSS 反而降到
> 99 MB）。A/B 确认归属后已**整套回滚**，板子留在上一版（只含 TLB 修复）上。
> 这一篇记录证据与下一步的入口。

## 1. 问题

文件映射早就一次铺一片（`handle_page_faults_around`，16 页一批，文件页实测
0.08 次/页）；**私有匿名映射一次只装一页**。

## 2. 实现（已回滚）

`VmMapping::handle_anonymous_page_faults_around`：批次 16 页、裁剪到本映射范围、
只装 `None` 的页、读缺页装共享零页、写缺页一次分配整批 frame、整批只发一次
`for_range` 的 TLB 失效；`mmap` 里给私有匿名映射打开 `handle_page_faults_around`
（`MAP_POPULATE` 除外）。

`tlb-staleness` 里配套加了两地址模型与证明：

```
range_flush_equals_per_address_flush
  → 一次 for_range 失效 与 逐地址失效，对每个地址的服务结果完全相同
```

`cargo kani -p tlb-staleness` 4 个 harness 全过；这条证明是"批处理只发一次 flush"
所依赖的前提，留着给下一次尝试用。

## 3. 量到的收益（这些数字是真实的）

| 负载 | 原始 | 只修 TLB | + fault-around |
| --- | ---: | ---: | ---: |
| 单线程触摸 256 MiB | 2461.7 ms（2.00 次/页） | 1046–1517 ms（1.00 次/页） | **270.4 ms（0.06 次/页）** |
| 4 线程各 64 MiB | 1872.6 ms（1.99 次/页） | 1421.5 ms（1.00 次/页） | **280.2 ms（0.06 次/页）** |

QEMU 同样 1.00 → 0.06 次/页。`cargo osdk test` 432/0，`preflight` 通过，
32 MiB 随机写 sha256 读回一致，桌面启动后 `used 1022 MB`（无 RSS 膨胀）。

## 4. 第一次尝试在浏览器上翻车了

部署后 3 分钟：Firefox 窗口不出现、单核 100%、**缺页数 4,657,735 且以 30k/s 增长**，
`VmRSS` 只有 99 MB。A/B 确认归属，批大小压到 1 页仍复现。

最小复现最后落在一个 JIT 探针上（`mmap RWX → 写机器码 → mprotect RX → 执行`）：
板上它卡在 **call** 阶段，缺页 857 万次、RSS 448 kB、84% 内核态；同样的探针在
QEMU 里 1 秒内跑完。

## 5. 根因：软件 A/D 位（Svade）

采样打点显示反复缺页的那个页，PTE 标志是 `R`、**没有 ACCESSED**，而 `required=READ`。
也就是说：页已经映射、权限也够，访问却一直缺页。

EIC7700 的 MMU 把 accessed/dirty 位的更新交给软件（Svade）：PTE 里 A=0 时，**每一次**
访问都会触发缺页，直到软件把 A 置上。单页路径在"已映射且权限足够"的分支里调用
`record_page_access`（置 A 并 flush）；而批量路径直接返回成功，A 永远是 0——
于是每次访问都缺页，处理器不断返回用户态、指令不断重试。

QEMU 的 TCG 默认做硬件 A/D 更新（Svadu），所以仿真从来看不到这个现象。这也解释了
为什么只有 JIT/浏览器负载触发：`mprotect` 会重写 PTE、清掉 A 位，之后的每个访问都要
重新"缺"一次。

修复很小：那个分支改调 `record_page_access(&mut cursor, va, access)`，与单页路径一致。

## 6. 修复后的结果（板子）

| 指标 | 基线（只修 TLB） | 风暴版 | **修复后** |
| --- | ---: | ---: | ---: |
| 256 MiB 顺序触摸 | 1046–1517 ms | 270 ms（但会风暴） | **182.5 ms**（0.06 次/页） |
| 4 线程各 64 MiB | 1872.6 ms | 280 ms（但会风暴） | **246.1 ms**（0.06 次/页） |
| Firefox minflt | 177,021 | 4,657,735 | **39,930**，5 s 内不增长 |
| Firefox RSS | 415 MB | 99 MB | **394 MB** |
| Firefox 窗口 | 有 | 无 | **3 个** |
| JIT 探针 | 通过 | 卡死 | **通过**（2.00 次/页） |

相对只修 TLB 的内核：**顺序触摸 5.7–8.3×，多线程 7.6×**；Firefox 的缺页从 177k 降到
40k（批量装页让它更少了）。

回归：`cargo osdk test` 432/0；`cargo kani -p tlb-staleness` 4/4；preflight 通过；
板上无 failed unit、无 panic，`systemd-analyze` 不受影响（14.8 s）。

## 7. 经验

- **仿真看不到硬件语义**：Svade/Svadu 的差别让同一份内核在 QEMU 与板上表现完全不同。
  凡是接触页表位、TLB、缓存的改动，真机验收不可省。
- 最小复现探针比"跑浏览器看现象"快两个数量级：一个 40 行的 JIT 探针把"浏览器卡死"
  变成"2 分钟一轮"的实验。
- 验收清单固定为：JIT 探针通过 + Firefox 窗口出现 + minflt ≤ 基线且空闲不增长 +
  RSS 正常 + 微基准 0.06 次/页。

## 8. 还能再要的

- 批大小可调（16 是 Linux 默认值）；
- 现在只在"缺页页已映射且权限够"时记录 A 位；批量里其它已映射页的 A 位没动，
  它们各自缺一次页时再补（正确，但不最优）。
