# 范围 TLB flush 的尝试（未达目标，已 revert）+ 成本形状实验

日期：2026-10-26
内核基线：`5061dd6a8`
本轮改动：`vm_space.rs` 的 unmap 循环合并连续页 flush（已 **revert**，见 §2）

## 0. 结论

1. **合并逐页 flush 只把 madvise 从 90.7 µs 降到 82.8 µs（−8.6 %），远未达到 <40 µs**，
   按纪律 revert，内核回到 `5061dd6a8` 的状态。
2. 随后的形状实验（§3）说明原因：**成本由 madvise 的「范围大小」决定，而不是 flush 条数**。
   8 MiB 范围即使**一个页都没映射**也要 **78.6 µs**；成本随范围里的已映射页数再线性叠加
   （2048 页时 692 µs ≈ 300 ns/页）。
   也就是说，瓶颈在**按范围逐项走页表（`take_next`/`find_next_impl`）**，不在 flush 操作的数量。
3. 任务 B（延后 `sync_tlb_flush`）评估结论：**不建议**，判据见 §4。
4. 任务 C：**glibc 没有拆分**——A1 里 1000 次 create/join 对应恰好 **1000 次** madvise，
   一个线程一次调用（见 §5）。

## 1. 任务 A：改动内容（已 revert，留档）

`ostd/src/mm/tlb.rs` 新增 `TlbFlusher::issue_frame_for_flush()`（把「延迟释放的 frame」单独入栈，
`OpsStack::push_frame` 从原 `push` 中抽出），`ostd/src/mm/vm_space.rs` 的 `unmap` 改为：
连续映射页累积成一个 run，遇到空洞/IO 映射/末尾时发**一条** `TlbFlushOp::for_range(start..end)`，
frame 仍逐个进 `frame_keeper`，`dispatch_tlb_flush()` 时机不变。

设计上是自洽的（flush 与 frame 释放的先后关系未变），但收益不足，遂放弃。

## 3. 成本形状实验（SH1，基线内核上做的）

固定 madvise 范围 8 MiB，改变实际触碰（=映射）的页数：

```
t0    touch=0    avg=78601 ns
t1    touch=1    avg=96835 ns
t512  touch=512  avg=183757 ns
t2048 touch=2048 avg=692125 ns
```

固定 512 页被触碰，改变 madvise 范围：

```
r256_512   range=256 KiB  avg=104677 ns
r1024_512  range=1 MiB    avg=316551 ns
(8 MiB 同条件见 t512 = 183757 ns)
```

| 观察 | 数字 | 含义 |
|---|---|---|
| 8 MiB 范围、**0 页映射** | **78.6 µs** | 光是走这个范围就要 ~79 µs ⇒ 范围大小是主项 |
| 每多一个已映射页 | 约 +300 ns（2048 页时 692 µs） | 页级成本叠加在范围成本之上 |
| 256 KiB 范围、512 页触碰（只覆盖前 64 页） | 104.7 µs | 范围小 → 便宜 |

结论：**先修「按页走范围」的遍历**（理想情况下应跳过整段未映射区域，用页表树跳过空子树），
而不是继续优化 flush 操作数。`take_next` → `find_next_impl(len, true, true)` 的参数与行为
是下一轮的第一站（`ostd/src/mm/page_table/cursor/mod.rs:533`）。

## 4. 任务 B：`sync_tlb_flush` 能否延后（只评估）

**结论：不建议在没有 lazy-TLB 设计的情况下延后。**

判据（三条都要成立才可行）：
1. **安全性**：unmap 之后映射页可能立刻被回收给其他用途；若远端 CPU 的 TLB 还持有旧项，
   它可以在 flush 之前继续写这块物理页 ⇒ 数据破坏。现有 `RcuDrop` 只保证 **RCU 宽限期**，
   RCU 宽限期不蕴含「该 CPU 已 flush TLB」（它可以一直在用户态跑而不经过静止点）。
2. **语义**：`madvise`/`munmap` 返回后，Linux 保证其他线程立刻看不到这些页；延后 flush 会破坏这一点，
   除非引入「每个 mm 的 pending flush 列表 + 用户态返回/上下文切换时兜底执行」的机制（即 Linux 的
   lazy TLB + `tlb_finish_mmu` 的变体），这已经是设计级改动。
3. **收益**：本轮 A 已证明 flush **条数**不是瓶颈（合并后只省 8.6 %），延后同步等待最多也只能碰到
   那 18 µs 固定成本的一部分——收益/风险比不划算。

**给下一轮的判据**：若要做，必须先有「远端 CPU 在 reenter user mode 前必然处理 pending flush」的实现，
并用一个专门的并发测试（一个 CPU 循环读 unmap 区域、另一个 unmap + 立即复用物理页）验证无脏写。

## 5. 任务 C：glibc 是否分多次小 madvise

**否。** MD1 的 A1 是 1000 次 create/join，madvise 计数恰好 **1000**（`count=1000`），
A2 同样 `count=1000` ⇒ glibc 每个线程退出只做**一次** `madvise(MADV_DONTNEED)`，
范围是整个栈（8 MiB / 128 KiB）。
