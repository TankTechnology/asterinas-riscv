## 阶段结论

### 1) fast ladder（r141，已写收据）

- L0：`firefox-esr --version` = `Mozilla Firefox 140.16.0esr`，rc=0。
- L1：`glxtest` = `RENDERER virgl`、`/dev/dri/renderD128`、`TEST_TYPE EGL`，rc=0。
- L2（30s）：headless 截图超时，无截图、无 MOZ_LOG。
- L2b（120s）：rc=0、93.5s、截图 20146B；日志 `WebRender - OpenGL version new 3.2`、
  `Renderer: Software WebRender`、`is_software: true`。
- 结论：**WebRender 能在 guest 初始化**，但冷启动约 93.5s 且是 Software WebRender；
  30s 上限低于冷启动包络。
- MOZ_LOG 在该 Debian 构建里**不产生文件**（NSPR 日志被编译掉或未启用），IPC 级
  消息日志不可用；后续不再依赖它。

### 2) windowless（r148/r149）

- 请求 `{"moz:windowless":true}` 被 Marionette 拒绝：
  `session not created: moz:windowless only supported on MacOS`
  （`driver.sys.mjs` 中 `moz:windowless` 仅在 macOS 生效）。
- 结论：**windowless 路线关闭**，NewSession 必须等初始窗口。

### 3) 主线程卡点（r22、r152、r153 一致）

符号化栈（libxul dbgsym，build-id `286be09c…`，r-x 段 delta `+0x1000`）：

```
nsWindow::OnMap
  → nsWindow::ConfigureCompositor
  → nsWindow::ResumeCompositorImpl
  → PCompositorBridgeChild::SendResume
  → MessageChannel::Send
  → MessageChannel::WaitForSyncNotify   (pthread_cond_wait)
```

r147 时间线：NewSession 发出后 ~42s，主线程与 Compositor 线程在同一毫秒
（`entered_jiffies=236988` / `236989`）分别进入 futex。r152 该间隔为 ~78s。
**窗口映射时机在 42–78s 之间漂移**，固定偏移 poke 会打空。

### 4) poke 系列：不是简单丢失唤醒

r151（固定偏移，打在真正卡死之前）与 r152（3s 锚定，锚到一次 3.3s 的瞬时等待）
都只证明“目标线程能醒”，不能证明“卡点”。

r156 用 **10s 锚定**（`PROBE_BLOCK detected=1 age_jiffies=10431`）在真正卡死后依次 poke：

| 目标 | 结果 |
|---|---|
| renderer | 唤醒（schedstat +0.95ms，+1 switch），**重新进入同一个 ppoll**，无数据 |
| io (IPC I/O) | 唤醒，重新进入 epoll_pwait |
| compositor | 唤醒，重新进入 futex（`SynchronousTask::Wait`） |
| renderer（二次） | 同上，重新进入 ppoll |
| all（进程级 SIGCONT） | 主线程唤醒（+0.88ms），重新进入 `WaitForSyncNotify` |

结论：**所有线程都能被信号唤醒并重新检查自己的等待对象，且都没有待处理工作**。
因此不是“某一条 futex 唤醒丢了”，而是等待的条件本身没有发生。

### 5) 卡点链：main ← compositor ← renderer ← X

- 主线程：`PCompositorBridgeChild::SendResume` 同步 IPC，等 compositor 的 Reply。
- Compositor 线程栈（r153 符号化）：
  `RecvResume → WebRenderBridgeParent::Resume → WebRenderAPI::Resume`，
  源码 `WebRenderAPI::Resume()` 在 `RenderThread::PostEvent(...)` 后调用
  `SynchronousTask::Wait()`（无超时 condvar，futex op 393，`arg3=0`）。
- Renderer 线程：`ppoll(fd=9, events=POLLIN)`，**只有一个 fd**，target `socket:[…]`；
  r152/r155/r156/r157/r160 均为 `revents=0`。单 fd + socket 是 libxcb
  `_xcb_conn_wait` 的形态 → renderer 在等 X 连接的 reply/event。
- Xorg：r157 `PROBE_EXTERNAL pid=134 name=Xorg syscall=epoll_pwait`，
  entered_jiffies 很新 → **Xorg 没有卡在驱动等待里**；同期 xwininfo/xdpyinfo 均成功。

即：renderer 在 `Renderer::Resume`（`RendererOGL::Resume → CompositorOGL::Resume
→ gl()->RenewSurface(widget)`，GTK 路径）里同步等 X，而 X 服务器没有回它；
compositor 等 renderer 的 `SynchronousTask`；主线程等 compositor。

### 6) X 侧排查

- r155：`PROBE_WINDOWS` 的 xwininfo 成功，Firefox 窗口 `Mozilla Firefox 1152x689` 已在
  X 树中 → X server 对其他客户端正常。
- r157：Xorg 主线程在 `epoll_pwait`（idle），`Xorg:disk$0` 在 condvar 等待，均无长阻塞。
- r159（`asterinas.dri_trace=1`，bootarg 必须插在 ` -- ` 之前）：1585 条 `DRI_IOCTL`，
  **0 条 REFUSED**（未知命令直接 ENOTTY，不进 REFUSED 日志）。
  命令分布以 `VIRTGPU_WAIT`(296)、`EXECBUFFER`(264)、`TRANSFER_TO_HOST_3D`(247)、
  `RESOURCE_CREATE`(174) 为主；**没有 PAGE_FLIP**，呈现走 `MODE_DIRTYFB`。
  另有 2 次 `CRTC_GET_SEQUENCE`（0xc01064c7，驱动未实现 → ENOTTY）。
- r160：在真正卡死后先跑两次 `xwininfo`（X stimulus，rc=0），再 poke renderer；
  renderer 仍重新进入 ppoll、`revents=0`、session 不推进。
  → **请求不是“躺在 Xorg 未读队列里”**（否则 stimulus 会让 server 重扫并回复）。

## 追加：SWGL 对照（r161/r162，2026-10-21 晚）

r161 在 unit 里加 `ASTERINAS_FIREFOX_WEBRENDER_SOFTWARE=1`（`gfx.webrender.software=true`
+ `LIBGL_ALWAYS_SOFTWARE=1` + `MOZ_X11_EGL=0`），其余探针不变，超时 300s：

- Marionette 仍到 `Waiting for initial application window`，300s 内没有 NewSession 响应；
- **Renderer 线程不再出现在 ppoll**（无 `PROBE_POLLFD name=Renderer`）；它处于 `R`，
  当前 syscall 66 = `writev`，sequence=6204，说明软件光栅化在工作；
- 主线程在 receipt 时**不在 `SendResume`**：`futex op=128 expected=2`（互斥锁），
  栈是 `nsAppShell::ProcessNextNativeEvent → PollWrapper → nsThread::ProcessNextEvent`
  的 GTK/GLib 事件循环；
- 浏览器日志有 `WaitFlushedEvent::Run: is delayed: 5241 (t=173.298)`。

结论：SWGL 绕开了 EGL resume 的死锁（主线程恢复事件循环），但软件首帧在 TCG 下
非常慢，300s 内没完成 NewSession。r162 用 600s 预算验证“给足时间 SWGL 是否能返回”。
该结果决定是否存在一条“功能可启动”的软件路径，以及 EGL 路径是否是唯一卡点。



1. **Renderer 侧的同步 X/GL 等待等的是一个不会发生的回复**：请求可能从未发出
   （xcb 输出缓冲/线程交互），或是一个需要对方先有动作的 X 事件（Present/DRI3 完成）。
   现有证据只能确定“X 连接上无数据、Xorg 未卡、stimulus 无效”。
2. `RenewSurface` 在 Mesa EGL/DRI3 路径里销毁/重建 surface 时等待旧的 Present/
   buffer release；该等待在协议上依赖一个没被触发的完成事件。
3. 内核 DRM 事件/翻页未实现（`DriHandle.events` 从不 notify、PAGE_FLIP 拒绝 flags、
   `CRTC_GET_SEQUENCE` ENOTTY）可能在某些客户端路径上造成等待，但 r159 未看到
   PAGE_FLIP，故降为次要假设。
4. 已排除：Marionette 传输、TCP、windowless、glxtest/virgl 不可用、单纯 futex
   wake 丢失、Xorg 整机卡死。

## 追加：SCM_RIGHTS / DRI3 假设与修复（r164/r165）

沿 DRI trace 继续检查内核时发现一个具体缺口：

- `PRIME_HANDLE_TO_FD` 返回的文件类型是 `device/dri/prime.rs` 里的 `DmaBufFile`
  （自定义 `FileLike`，不是 `InodeHandle`）。
- Unix socket 的 `SCM_RIGHTS` 发送路径（`net/socket/unix/ctrl_msg.rs`
  `classify_scm_file`）只把 `InodeHandle`（正则/管道等）、`EpollFile`、非 Unix
  socket、`PidFile` 视为 `ProvenLeaf`；其余一律 `Unsupported`，发送时在
  `try_write` 里直接返回 **EPERM**（`"SCM_RIGHTS contains a file container
  unsupported by B1"`）。
- X11 的 DRI3（EGL 与 GLX 两条路径都用）需要把 **dma-buf fd** 通过 X socket 的
  SCM_RIGHTS 传给 Xorg。按上述分类，Asterinas 会拒绝该发送。

修复（内核 `b40ef616…`）：

- `FileLike` 新增默认方法 `is_scm_rights_leaf() -> bool`；
- `DmaBufFile` 与 `FenceFile` 返回 `true`（它们只描述内存/提交，不持有其它文件描述符）；
- `classify_scm_file` 把这类文件归为 `ProvenLeaf`。

r164（默认 EGL + 修复内核，300s）行为发生明显变化：

- Renderer 不再停在 `ppoll(fd=9)`；它处于 `writev(fd=9)`，累计 **80.5s** CPU、
  4230 次切换，持续向 X 连接写请求；栈中出现 `libEGL_mesa` 与 `libX11` 帧。
- Xorg 主线程在 `recvmsg(fd=28)` 活跃处理请求（修复前是 idle epoll）。
- receipt 时 `xwininfo` **超时**（`PROBE_WINDOWS {"error":"TimeoutExpired"}`），
  说明 Xorg 被 Firefox 的请求流占用，5s 内没轮到外部客户端。
- 主线程仍在 Xlib 的互斥锁上（futex op=128 expected=2），NewSession 300s 未返回。

解释：硬死锁（客户端等一个永不到来的 X 回复）消失了，剩下的是**首帧在 TCG 下
渲染极慢**，与 SWGL 对照臂的形态一致。r165 用 600s 预算验证 EGL+修复能否在预算内
完成 NewSession。

## 追加：about:blank 臂与 virtio-gpu 自旋锁 panic（r167/r168）

SCM 修复后窗口已能映射（r165 `PROBE_WINDOWS` 里有 `Asterinas DRM Firefox sce...`），
但 scene 作为启动页会让初始窗口的主线程一直忙于场景动画，NewSession 在 420–600s
内仍不返回。r167 改用 `ASTERINAS_FIREFOX_START_URL=about:blank`，计划先建会话再导航。

r167 没有跑完：guest 在启动过程中内核 panic：

```text
MIGHT_SLEEP_VIOLATION cpu=3 preempt_count=1
caller=kernel/comps/virtio/src/device/gpu/device.rs:996:44
ATOMIC_GUARD_TAKEN file=ostd/src/sync/spin.rs line=74 column=27
PANIC_ENTRY ...
```

根因：`present_framebuffer` 里

```rust
if let Some(prev) = *self.present_resource.lock() {   // SpinLock 临时守卫活到 if-let 结束
    let _ = self.resource_unref(prev);                // 这里会等待 virtio 控制队列（可睡眠）
}
```

`present_resource` 是 `SpinLock<Option<u32>>`，而 `resource_unref` → `control_queue.lock()`
是睡眠路径；第二次 present 就会触发 panic。修复：先把 id 拷贝出来、释放守卫，再 unref。

内核修复累计两处：

| 修复 | 内核 sha256 |
|---|---|
| SCM_RIGHTS dma-buf/fence leaf | `b40ef616cbd575c3c21ff78f6cbbc5f9ba0ba9659a8d4243f59c370fabe07663` |
| + present_framebuffer 自旋锁作用域 | `9dd10be224b2d1df8a34c7084ea453de69199b56f977334ecda665d950d1a078` |

r168 = about:blank + 上述两处修复，300s 探针；用来判断“先建会话、再导航场景”
是否能拿到 NewSession。

**r168 结果：NewSession 通过。**

```text
FIREFOX_DRM_PROBE_BOUNDARY name=greeting status=pass
FIREFOX_DRM_PROBE_BOUNDARY name=new-session status=pass
FIREFOX_DRM_PROBE_WINDOWS ... "Mozilla Firefox" 1280x747 ...
FIREFOX_DRM_PROBE_DONE status=pass phase=new-session reason=NewSession_returned_a_sessionId
```

主线程在 GTK 事件循环（pollfd: eventfd / socket:[416] / pipe），不再卡在
`SendResume`；窗口为 `1280x747` 的 Mozilla Firefox。即：

- SCM_RIGHTS 的 dma-buf/fence leaf 修复解除了 EGL/GLX resume 的硬死锁；
- `present_framebuffer` 的自旋锁作用域修复避免了第二次 present 的内核 panic；
- 以 `about:blank` 作为启动页、NewSession 后再导航到场景，可以正常建立会话。

## 追加：完整场景门禁与 GEM 池耗尽（r169/r170）

r169（完整场景门禁，blank 启动 → Navigate 到场景，内核 `9dd10be2…`）：

- `FIREFOX_DRM_BOUNDARY name=new-session status=pass`（elapsed ~296s）；
- 随后 `WebDriver:SetWindowRect` 阶段 `Marionette_read_deadline_expired`，
  `_one_run` 失败；
- 浏览器日志出现 `[GFX1-]: RenderThread::InitDeviceTask is slow`、
  `NewRenderer::Run is slow`、`[GFX1-]: wr_renderer_render: Out…`（被 200B
  截断，`OutOfMemory` 最可能）；
- Firefox RSS 约 334 MiB。

结合内核注释：DRM 的 GEM 池是 **64 MiB、只增不减的 bump allocator**
（`DUMB_POOL_SIZE`，`reserve_span` 的注释说明：mmap 返回整个 pool，所以释放的
span 不能复用）。WebRender/glamor 的首帧分配量超过 64 MiB 时，`CREATE_DUMB`
返 ENOMEM，Mesa `gbm_bo_create` 失败，WebRender 报 OutOfMemory 并关闭渲染。

修复（诊断用）：内核新增 boot 参数 `asterinas.dri_pool_mb=N`（16..1024，默认 64），
`desktop_m4_gate.py` 支持 `ASTERINAS_DRI_POOL_MB`（插在 ` -- ` 之前）。
r170 = 完整场景门禁 + 256 MiB 池（内核 `1bffe7d7…`）。

遗留风险：bump allocator 的上限是**生命周期累计分配**，不是同时存活量；
长时间动画场景仍可能耗尽，即使是 256 MiB。彻底的解法是实现 windowed
`Mappable` 后允许复用 span，或为 3D 资源使用独立可回收池。

## 追加：场景导航的 15s 命令上限（r170/r171）

r170（256 MiB 池，完整场景门禁）：

- NewSession pass（~288s）；
- `SetWindowRect`、`GetWindowHandles`、`SwitchToWindow`、transport probe、
  `ExecuteScript` 全部在 350–351s 内通过；
