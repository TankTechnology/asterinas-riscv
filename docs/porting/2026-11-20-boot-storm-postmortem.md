# Megrez 启动风暴复盘（2026-11-19 → 20）

一台 RISC-V 开发板"随机重启"了几天。真正的原因是一条被配置成不屏蔽的电平触发中断；
真正拖慢定位的，是我们自己的观测手段反复骗过我们。

## 结论先行

xHCI（USB 主机控制器）的中断线是**电平触发**：只要控制器的事件环没被取空，线就一直有效。
驱动注册时用了**不屏蔽**的映射，而中断上半部只做了一件事——唤醒一个线程。于是这条线被反复
重投，实测约 **每秒 63 万次**。

在 RISC-V 的 PLIC 上，一个 hart 取中断是个循环。风暴进来后它出不了这个循环，既不跑调度器、
也不喂硬件看门狗；**10.7 秒**后看门狗复位整机。下一次启动是否撞上，取决于启动瞬间的 USB 状态
和哪个 hart 接到这条 IRQ——所以它看起来像"随机重启"。

**修复**：注册改为映射即屏蔽（`map_fdt_pin_to_masked` + `on_active_and_mask`），取空事件环之后
再 `rearm()` 解除屏蔽。另外加一层通用安全网：单次陷阱最多接受 4096 个外部中断，超出即屏蔽该源
并打印 `ASTERINAS_IRQ_STORM`；心跳里增加 `storms=` 字段，让"风暴"以后能被直接看见。

## 失效链条

1. **电平触发**：事件环未取空，中断线持续有效。
2. **注册未屏蔽**：处理返回后 PLIC 立刻重新投递同一源。
3. **上半部不取环**：只唤醒线程，环里的条目原样留着。
4. **正反馈**：每秒约 63 万次中断，CPU 时间全部花在进出陷阱上。
5. **hart 被锁死**：PLIC 取中断的循环出不来，调度器停摆、心跳停摆。
6. **看门狗收尾**：10.7 秒无喂狗 → SoC 复位 → 下一轮启动可能重蹈覆辙。

## 为什么定位花了这么久

根因只是两行代码，但现象同时具备三个让人误判的特征：**时好时坏**（取决于启动瞬间的设备状态）、
**没有任何内核输出**（复位由硬件发起，不是 panic）、**每次死法还不一样**（有时 10 秒复位，
有时静默挂起）。这三个特征合起来，最容易被解释成"硬件不稳"或"内存坏了"。

更麻烦的是，观测工具本身也在制造假象。下面每一行都是我们**相信了一个没有经过验证的结论**。

## 我在这次调试里犯的错

| 错误 | 表现与代价 | 正确做法 |
|---|---|---|
| 把"标记年龄"当成"卡在这里" | `print_write age=999.5ms` 被读成"在控制台里卡了 1 秒"，据此判断内核已失去响应 | 标记是**上界**不是位置；同一窗口里另一个陷阱在 6.8 ms 被取到，就足以证伪"中断已关" |
| 偏移到墙钟的映射用错基准 | 用行首偏移算到达时间，把"行之后的静默"算到这一行头上，得出"1.101 s 复位""31 s DDR 空窗"两个假结论 | 必须用 `offset + len`（整行写完）作为到达时刻 |
| 子串匹配当整词匹配 | `ASTERINAS_PANIC_REBOOT` 命中的是 `ASTERINAS_PANIC_REBOOT_ARMED`（武装提示），把正常启动报成 panic；`unmapped` 命中的是 "unmapped key code" | 判据用完整形式（`ASTERINAS_PANIC_REBOOT message=`），每条通道再配一个负向探针 |
| 把"传了参数"当成"参数生效" | `ARCH=riscv64` 构建，Makefile 只认 `TARGET_ARCH`，静默用 x86 跑了一轮"验证"；同类第三次：命令行覆盖 `CARGO_OSDK_TEST_ARGS` 冲掉 `--scheme riscv`，日志其实是 `Finished dev profile`，却据此宣布"release 也失败" | 只看构建日志里的实际取值（`Finished \`X\` profile`、真实 QEMU 二进制名） |
| 把退出码当成判据 | `make ktest-local` 在有测试 `FAILED` 时仍返回 0 | 绿不绿只解析 `test result:` 行 |
| 过滤器当成子串 | `KTEST_FILTER=ext2` 得到 `0 passed; 254 filtered out`——一个用例都没跑，输出却像通过 | 给完整后缀，或整 crate 跑；跑完单独 grep 新用例名确认真的执行过 |
| 工具有 I/O 缺陷却当成被测对象结论 | 崩溃门禁靠"读到一行输出"判断何时断电，而内核为测试撑开的 1500 ms 窗口里**一个字节都不打印**，读数永远阻塞到窗口关闭——"有修复"和"无修复"两个内核都报 `dangling=0` | 按下电/杀进程必须按**时间**触发（读放独立线程）；并且必须有一个"应当失败"的对照组 |
| 拿到能对上数量级的机制就宣布根因 | 发现"每次中断只加 1、而截止时间按周期追赶"，立刻当成时钟慢 4.4% 的原因；实际心跳增量中位数是 1004 ms 而非 957 ms，tick 根本没丢 | **"机制能解释现象"不等于"机制就是原因"**；先用最便宜的数据把假设杀掉 |
| 为拿诊断窗口关掉安全网 | 在 U-Boot 里关掉硬件看门狗再手工引导，内核在同一处挂死且无看门狗 → 板子永久停住，只能请人断电（同类第二次） | 看门狗正在复位**不是故障**；要稳定窗口就保留看门狗、mask 桌面单元 |
| 没查"是否已有人做过"就动手 | 用半小时实现 ext2"拒绝重复释放"，事后发现两项工作在另一条分支上已完成 | 动手前先 `git log --all -S '<关键符号>'` |
| 把配置问题当成回归 | 重启后进入复位循环，第一反应是"修好的内核又坏了"；实际是默认 `bootcmd` 加载旧内核，任何 `reboot` 都会掉回去 | 先看启动的到底是哪个镜像，再谈回归 |

## 真正有效的定位手法

### 一、裸探针，一层一层剥

当"零输出"可能是控制台、格式化、锁、栈任何一层的问题时，最快的办法是**绕过所有中间层直接
写字节**：入口处直接调 SBI 写字节把标记打到串口，标记出现就证明"内核到了这里、控制台通"；
再在可疑调用的前后各打一个字节，只看见前一个就说明故障在调用内部。两次探针把范围从
"整个启动过程"缩到"一次格式化"。

### 二、A/B 对照，而且必须有一个"应该失败"的组

验证 ext2 写序修复时，同一个门禁、同一套参数跑两个内核：一个带写序、一个只有同一处崩溃点但
不带写序。后者 3/3 报 `dangling=[12]`，前者 3/3 干净。没有这个"应该失败"的组，我们手里就只是
一台永远不会失败的仪器。

### 三、用两个计数区分"整机复位"和"原地重启"

一次启动里入口被重进 4312 次，而 OpenSBI 横幅只出现 1 次——这两个数字放在一起就说明：不是
整机复位，是陷阱帧把 CPU 送回了入口。单看任何一个计数都会得出错误结论。

### 四、给仪器本身找旁证

门禁"通过"还不够，还要一条能证明它**打中了**的旁证：杀点落在窗口内时，被测程序来不及打印
第二轮标记，所以"日志里只有一行 `CHURN`"就是窗口命中的证据；两行说明杀晚了。

### 五、每条结论绑定到确切的镜像

两个工作树共享构建目录时同名产物会互相覆盖。每次跑完立刻复制镜像并记 `sha256`，结论里带上它
——否则"基线"和"修复"可能是同一张图。

## 修复之后

修复版内核连续三次默认配置启动都进入桌面，分别用 **15.100 / 15.184 / 15.072 秒**；心跳
`storms=0`；随后连续运行 **8 小时 11 分钟**。当晚主动重启并断电恢复后，同一镜像再次在
**15.544 秒**到达桌面，`storms=0`。

## 仍待处理

- **默认 `bootcmd` 指向旧内核**：任何一次 `reboot` 都会退回没有修复的镜像；修改需要 `saveenv`。
- **其它驱动**是否存在同样的"电平触发 + 不屏蔽"写法（安全网能兜住，但根因应逐个查）。
- **内核单调时钟比墙钟慢约 4.4%**：判别依据是 Jiffies 与 TSC 一起偏（指向时基声明偏高），
  但安全的测量手段还没有（U-Boot 读 ACLINT 会让 U-Boot 自己复位）。

## 下次可以直接照做的清单

- 动手前先查"是否已经有人做过、是否已经验证过"。
- 相信一个参数之前，先在日志里看到它生效的样子（profile 行、真实二进制名、参数被内核承认）。
- 相信一个门禁之前，先让它在一个**应该失败**的对象上失败一次。
- 判据用完整形式匹配，并给每条通道配一个负向探针。
- 任何"板子没反应"的结论之前，先问：观测工具此刻会不会给出同样的结果。
- 任何"拿诊断窗口"的动作之前，先问：失去看门狗之后我还能自恢复吗。
- 拿到能解释现象的最小机制时，先用最便宜的数据把它杀掉一次，再升级为根因。
