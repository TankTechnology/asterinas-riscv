## 2. 任务 B：VmSize（466 GB vs 447 MB）——定位到两处，修补失败

### 2.1 两处根因（文件:行号）

| # | 位置 | 问题 |
|---|---|---|
| 1 | `fs/fs_impls/procfs/pid/task/status.rs:159-166` | `vsize = get_mappings_total_size()`（**字节**）直接以 `kB` 标签输出，**少除 1024** |
| 2 | `vm/vmar/vmar_impls/mod.rs:288-320` `insert_try_merge` | 新映射加进 `total_vm` 后，与 prev/next 合并并 `self.vm_mappings.remove(&addr)` 时**没有把被合并掉的映射 size 从 `total_vm` 减掉** ⇒ 每次 merge 泄漏一份，单调膨胀（Firefox 大量拆分/合并 → 466 GB） |

### 2.2 修补尝试与失败（如实记录）

把两处都改掉后（单位 `/1024` + 两处 `total_vm -= removed.map_size()`），内核在**引导 11 s 处 panic**：

```
Uncaught panic: attempt to subtract with overflow
	at kernel/core/src/vm/vmar/vmar_impls/mod.rs:312
```

说明存在「要减掉的映射并未计入 `total_vm`」的路径（同一次插入里 prev/next 合并链可能重复访问同一邻居）。
第二次尝试改成 `saturating_sub`，但**该补丁因断言失败没有真正应用**（编译 0.26 s、未重编），
于是第二次上板跑的仍是崩溃版、同样 panic。**这是我的失误，已记录。**

时间盒用尽，**两处 VmSize 改动全部 revert**（`git checkout`），当前工作树等价于 `0afe3b2ee`。

### 2.3 下一轮的直接落点

1. 先只上**单位修复**（`/1024`），风险最低；它能把 466 GB 变成 466 GB/1024 ≈ 455 GB，
   仍然异常，说明泄漏才是主项——但可先单独验证不崩。
2. 泄漏修复要**同时处理合并链**：把 `total_vm` 的维护改成「按最终 `vm_mappings` 里所有映射求和」
   的调试校验（或用 `saturating_sub` 并加一条 debug_assert 记录不一致次数），再决定对外数值。
3. 验证口径：Firefox 主进程 VmSize 应落到 Linux 同量级（Linux 侧 447 MB 那次可能选到 wrapper，
   下一轮应同时打印进程 cmdline 以确认选的是同一个进程）。

## 3. 任务 C：用修好的计数器重算三份账

| 项 | 旧口径 | 新口径（`0afe3b2ee`） |
|---|---|---|
| Firefox 主进程 stime（8 s 热轮） | 133 ticks（1.33 s） | **12 ticks（120 ms）** |
| utime | 31 ticks（310 ms） | **3 ticks（30 ms）** |
| 内核态占比 | 81 % | **80 %（但基数只有 150 ms）** |
| syscall 合计（同窗口全系统） | 134.8 ms | 134.8 ms（不受单位影响） |
| 缺页合计（上一轮） | 61.3 ms | 61.3 ms |
| 调度五段（上一轮） | 135.9 ms | 135.9 ms |

**新排序与一句结论**：

1. **syscall（134.8 ms）≈ stime（120 ms）** ⇒ 修好单位后**内核时间几乎全部可以由 syscall 解释**，
   「84 % 未归因」是单位换算造成的假象，**不存在缺失的第四个桶**。
2. 内核侧的下一步应当是**单次 syscall 成本**（CAL2 已量到：我们 getpid ≈0.9 µs vs Linux ≈0.055 µs，
   **16×**；clone 4.92 ms/次、openat 36 µs/次），而不是调度/tick/缺页——后三项加起来
   （135.9 + 61.3 ms）都在 syscall 量级以下。
3. 进程自身 CPU 只有 150 ms / 8 s ⇒ **Firefox 的绝大部分墙钟时间既不在用户态也不在内核态**，
   而在等待（IO/IPC）。若继续优化，应该转向**等待路径与应用侧**，内核 CPU 已不是主要瓶颈。
