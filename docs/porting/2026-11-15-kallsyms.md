# 内核符号表（kallsyms）：阶段 0 落地（2026-11-15）

可观测性/C 计划的第一步。跟踪和采样最终都要把“一个地址”变成“哪个函数”，
所以先有符号表；后面 ftrace 打印 `func:`、采样 profiler 聚合热点都直接用它。

## 1. 设计

符号表只能在内核链接完成之后才有，而编译器又必须“看到”它才能把它放进镜像，
于是分成两半：

1. **内核侧预留一块固定区域**（`kernel/src/trace/kallsyms.rs`）：
   `magic: ASTERKALLSYMSv1\0` + 2 MiB 数据区，整体是一个 `static`。
2. **构建后由工具填充**（`tools/riscv/ksym/kallsyms.py`）：从链接好的 ELF 读出
   符号，打包后按 magic 定位、写进镜像文件的对应位置。内核运行时通过
   `lookup(addr)` 二分查表，`/proc/kallsyms` 输出整张表。

数据区布局（小端，相对数据区起点）：

```
0   u32  version=1
4   u32  num_syms
8   u32  table_off
12  u32  names_off
16  u32  names_len
20  u32  reserved
24  u64  addr_base        # 表内偏移相对它
32       表项 x N          # (u32 off, u32 name_off)，按地址升序
...      名字区            # NUL 分隔，去重
```

名字取 `llvm-nm -C` 的反混淆结果并截断到 72 字节；实测链路占用
1.15 MB（78 974 个符号 + 12 181 个去重名字），2 MiB 预留还有余量。
构建后镜像从 6.9 MB 变成 9.0 MB。

## 2. 用法

```sh
tools/riscv/ksym/build_kernel.sh            # 规范构建：cargo osdk build + 打表
tools/riscv/ksym/kallsyms.py show  <image> [--grep 函数名] [--limit N]
tools/riscv/ksym/kallsyms.py lookup <image> 0xffffffff80200000 0x80200040
```

`build_kernel.sh` 就是原先那条 release 构建命令（PATH/OSDK_LOCAL_DEV/VDSO 都设好）
再加上打表；**凡是要部署的镜像都应经它构建**，直接 `cargo osdk build` 出来的镜像
仍然能启动，只是 `/proc/kallsyms` 为空。

## 3. 踩到的两个坑（都是真问题）

**（1）编译器把数据区的读取常量折叠掉了。** 第一版部署后板上 `/proc/kallsyms`
是空的，而文件里明明有数据。临时加日志才看清：`blob()[0]` 打印出来是 `0x01`
（真实字节），但 `read_u32(0)` 返回 `0`——因为静态初始化器写的是全零，编译器
“知道”那个地址是零，就把常量下标的读取折成了 0；二进制补丁在编译之后，它不可能
知道。修法：所有读取改走 `core::ptr::read_volatile`。kernel crate 是
`#![deny(unsafe_code)]`，所以要在这两个小函数上 `#[expect(unsafe_code)]`。

**（2）符号地址有两个空间。** ELF 里早期启动代码的符号是物理地址
（`_start` = `0x80200000`），其余是高位虚拟地址（`.text` 从 `0xffffffff80245000`
开始）；另外还有 `__executable_start = 0` 这种链接器定义的绝对符号。表里统一
归一化到高位（`phys | 0xffffffff00000000`），并丢掉 `0xffffffff80000000` 以下的
绝对符号——否则 32 位表内偏移直接溢出。内核侧 `lookup()` 对拿到的地址做同样的
归一化，物理/虚拟两种形式都能查到。

## 4. 验收

| 项 | 结果 |
| --- | --- |
| 板上 `wc -l /proc/kallsyms` | 78 974 行，耗时 0.19 s |
| `head`/`grep` 关键符号 | `_start`=`ffffffff80200000`、`bsp_boot_entry`=`ffffffff80200040`、`__etext`=`ffffffff806b3dd0`，与本地 `llvm-nm` 完全一致 |
| 末行 | 最后一个文本符号 `__etext` |
| 归一化 | `lookup(0x80200040)` 与 `lookup(0xffffffff80200040)` 都命中 `bsp_riscv_image_header_end` |
| 用户地址 | `lookup(0x10)` → 无符号，不误报 |
| ktest | `unpatched_image_has_no_symbols`、`address_normalization` 各 1 passed（未打表镜像不 panic、返回空） |
| 回归 | preflight（结构 + QEMU 启动到用户态）通过；板上开机 `--failed` 为空、桌面正常 |

## 5. 下一步接口

`crate::trace::kallsyms::lookup(u64) -> Option<&'static str>` 和
`for_each_symbol()` 已经是阶段 1（环形缓冲里的 `func:` 字段）和阶段 4
（采样 profiler 的直方图）的输入；`/proc/kallsyms` 同时给用户态工具（比如以后
把采样结果翻成名字）提供了同一份数据。
