# PR #179 ext4 journal QEMU evidence

This receipt records the QEMU gates run against the PR #179 candidate combined
with the recoverable fbdev desktop changes. The candidate is based on
`origin/main` (`39a57d275dcc9253712acbe979d1c0ce1af347ed`) and ends at
`a02fecb5a36f1fdb44fd360abff9dc4b80f558f4`.

The root image was copied from the existing signed Debian image and converted
with `tools/riscv/debian/rootfs/convert_ext2_to_ext4_journal.sh`; the source
image was not modified. The resulting image SHA-256 is:

```
e72446e1b8f12f2f4a22bd45f1ce62a99b7548cdffff42f86fd9195a8f400006
```

All QEMU runs used the persistent development container, four RISC-V harts,
`FEATURES=riscv_sv39_mode`, `RELEASE=1`, `rootfs_type=ext4`, and an isolated
copy of that image. The following markers and exit statuses were observed:

| Gate | Result |
| --- | --- |
| `AUTO_TEST=ext4_regression` | `qemu_exit=0`, marker present, `e2fsck -fn` exit 0 |
| `AUTO_TEST=ext4_semantics` | exit 0; permissions, links, sparse, fallocate, xattr, fsync and syncfs marker present |
| `AUTO_TEST=ext4_directory_journal` | exit 0; create/delete/rename/growth/sync marker present |
| `AUTO_TEST=ext4_concurrency` | exit 0; four workers, 64 iterations, rename/rmdir/fsync/syncfs marker present |

The fault script emitted:

```

```

## QEMU desktop handoff and user-space blocker

The first `desktop_m4_gate` run used the ext4 image but did not pass an ext4
selector to stage1.  The stage1 transcript showed
`handoff-failed action=root-mount` and `DEBIAN_ROOTFS_FAIL reason=root-mount`.
The gate now carries an explicit `--root-fs=ext4` boot argument; a unit test
covers both the default ext2 mode and this ext4 mode.

With that selector, the rerun completed the stage1 root-mount, bind mounts,
chroot, and `exec` handoff.  Debian systemd reached multi-user, Xorg selected
the fbdev driver and opened `/dev/fb0` at 1280x1024, and the desktop service
started.  The run still failed its completion marker because `netsurf-gtk`
crashed while GTK loaded its `image-missing` icon.  The relevant transcript
contains:

```
Gtk:ERROR ... Failed to load ... image-missing.svg: Unrecognized image file format
Gtk ... assertion failed
DEBIAN_DESKTOP_M4_DIAGNOSTIC missing=netsurf
DEBIAN_DESKTOP_M4_FAIL reason=desktop-timeout
```

Changing the icon theme and supplying a PNG fallback produced the same
failure for a PNG file.  This distinguishes a missing SVG renderer from the
actual blocker: Debian's gdk-pixbuf loader modules are present, but the
runtime cannot load even the PNG module through its dynamic loader.  The
existing XFCE build path already documents the required remedy—build
gdk-pixbuf with `builtin_loaders=png,xpm`—and will be reused for the Debian
desktop overlay.  Until that overlay is built and its loader self-test passes,
the QEMU desktop gate and the physical desktop gate remain red.

The rerun artifacts are kept under
`target/qemu-ext4-pr179-desktop-m4-ext4-20261011-r3/`; the rootfs selector
change is in `tools/riscv/debian/rootfs/desktop_m3_gate.py` and is covered by
`tools/riscv/tests/test_debian_rootfs.py`.

The complete ignored artifacts are under
`target/qemu-ext4-pr179-20261011/`, including `result.json`, QEMU logs,
recovery logs and SHA-256 lists. These results qualify the QEMU ext4 path and
its fault-injection recovery behavior. They do not claim that the physical
board's installed Debian partition has been replaced; that requires a
separately staged, recoverable rootfs deployment and a watchdog-bounded board
cycle.

## Physical preflight

No experimental kernel or root-image replacement was performed in this
preflight. The board initially returned the RockOS root prompt, so a runner
that required U-Boot refused to continue. An explicit RockOS software reboot
then produced fresh OpenSBI and U-Boot output. The next RockOS boot reported
boot-id `b2b82327-654a-4d7e-aa12-eda60bc0526b`.

Read-only `e2fsck -fn /dev/mmcblk1p2` returned 4. It reported orphan-linked-list
corruption involving inode 1276 and a superblock last-write time in the future
relative to RockOS's current clock. The timestamp discrepancy alone does not
identify the cause of the orphan-list error. No filesystem repair was run.
The raw log is retained at
`target/megrez-ext4-physical-preflight-20261011-rockos-r2/serial.log`.

The layout query found a single 119.1 GiB SD device: partition 1 is a mounted
500 MiB ext4 boot partition, partition 2 is the unmounted 4 GiB
`ASTER_DEBIANM4` ext2 partition, and partition 3 is the mounted RockOS ext4
root. No separate writable test device was observed. Overwriting partition 2
without a verified backup and rollback is therefore not part of this receipt.

After the preflight, two distinct nonce-framed read-only commands proved UID 0
and the same boot-id, with the serial descriptor closed and reopened between
commands. The validated receipt is
`target/megrez-ext4-management-reopen-20261011/result.json`. The board was left
in RockOS with working serial root command access. SSH access was not checked
in this receipt.

## QEMU framebuffer registration and desktop-service diagnosis

The next QEMU run used the current kernel diagnostics and the historical
U-Boot contract. U-Boot injected the `simple-framebuffer` node, but the first
boot did not reserve the bochs BAR in `/reserved-memory`. The kernel therefore
reported no registered framebuffer even though the node was visible in the
serial log. The desktop boot command now grows the FDT, declares the fixed
scanout range as `no-map`, and prints both the reservation and framebuffer
nodes before `booti`; a source gate covers this ordering.

After that change, a root-console probe produced the following ordered facts:

```
RISCV_BOOT_FRAMEBUFFER status=found base=0x40000000 size=0x1000000 width=1280 height=1024 stride=5120 format=BgrReserved8888
ASTERINAS_FRAMEBUFFER_INIT status=found base=0x40000000 size=0x1000000 width=1280 height=1024 stride=5120
ASTERINAS_FRAMEBUFFER_INIT status=registered
crw------- 1 root root 29, 0 ... /dev/fb0
crw------- 1 root root 13, 0 ... /dev/input/event0
crw------- 1 root root 13, 1 ... /dev/input/event1
```

The same probe showed that the desktop service was blocked in
`desktop-input-identity` while reading variable-length evdev ioctl strings;
the evidence service was blocked in `systemctl is-active
systemd-logind.service` even though systemd had already started logind. The
rootfs gate now selects the fixed event0/event1 mapping only for the explicit
QEMU ordered profile, keeps strict ioctl identity for physical boots with a
five-second subprocess bound, and uses the live `systemd-logind` process as a
bounded readiness fact. The framebuffer diagnostics and these source checks
pass in the targeted Python suite (58 tests). A full QEMU desktop pass still
requires a freshly built signed root image containing these rootfs changes;
the physical board has not been retried.

## Fresh rootfs and scanout separation

A fresh signed `desktop-m4` root image was built from this checkout. Its
SHA-256 is
`461b9fa29230febf5b9056446a286786a0bfb35507b420637aa01a67cbd70a4d`.
With the ordered QEMU input profile, the guest reached all desktop markers,
including `DEBIAN_DESKTOP_M4_READY`, and reported a valid `fb0` sample with
`distinct=3 non_background=2`. The host HMP screendump still classified as a
single color, so this run proves the guest desktop and fbdev read path but not
host scanout.

Injecting `ASTERINAS_DESKTOP_M4_SCANOUT_PATTERN=1` as a second systemd kernel
environment assignment made the same boot stop after the Debian welcome line,
before desktop markers. The deterministic pattern is therefore kept as an
opt-in `desktop_m4_fbdev_canary_gate` diagnostic; the normal M4 desktop gate
does not enable it. This prevents a scanout experiment from destabilizing the
desktop startup contract. A separate canary run is required before claiming
host-visible QEMU pixels, and no physical retry was made.

The separate canary was then run once with the same fresh artifacts. It
reached `DEBIAN_DESKTOP_M4_FB_SCANOUT_READY`, observed three guest framebuffer
colors, and restored the original bytes exactly (`status=pass`). Its host HMP
capture still reported a single color, so the remaining defect is specifically
the QEMU bochs scanout/capture visibility path (or its cache/coherency contract),
not framebuffer registration, Xorg startup, or guest fbdev writes. The canary
receipt is retained under `/tmp/m4-canary-current` for this session and is not
treated as a passing host-display gate.

## Ext4 systemd two-boot gate

The dedicated `systemd-ext4-m3` rootfs was rebuilt from the current checkout,

ext4 replay failure. The short-timeout receipt is

## Framebuffer cache-policy A/B

To isolate the host-side single-color screendump, one QEMU canary was rebuilt
with the RISC-V firmware framebuffer mapped `Uncacheable` instead of the
current `WriteCombining` policy. The altered kernel did not reach the canary
completion marker within the 120-second bound; its serial log showed the
desktop service starting but no ready record. The experiment was reverted and
the normal `WriteCombining` kernel rebuilt (SHA-256
`9090874ef7cec90c8aac49b5d136100b724202e893d5fc2f692f2cdf58560814`). This
rules out a safe UC substitution as a drop-in fix; the remaining QEMU defect
is in the bochs scanout/HMP visibility contract or its capture path, while the
guest fbdev read/write and exact restore checks remain passing.

## `msync(2)` I/O-memory fix

The framebuffer userspace path calls `msync(2)` after writing the shared
mapping. Previously `msync` only looked for file-backed inodes, so an I/O
mapping returned success without issuing a device visibility operation. The
fix now identifies device mappings, releases the validation cursor, and flushes
the retained `IoMem` range. On Svpbmt-capable RISC-V, both uncacheable and
write-combining mappings use the architecture I/O fence; the EIC7700-specific
cache-register path is reserved for systems that need it.

With kernel SHA-256
`8a8be135abd770a76d5f05cda45c772ecbed38fa4aee8a324d128f565cdbbadd`, the
guest-only Desktop M4 receipt `target/qemu-desktop-m4-guest-only/result.json`
passed and recorded all desktop, fb0 and color markers. A raw host PPM captured
from the same kernel contains 43 colors, proving writes reach the emulated BAR;
it is still overwhelmingly black (only 103 of 1,310,720 pixels differ from the
background), so the standard one-percent host screenshot threshold remains
intentionally red. This separates the fixed guest I/O-memory visibility from
the remaining Bochs scanout/mode-programming issue.

## QEMU scanout capture timing and ablation

The earlier host screenshot was taken only after the final desktop marker.
The framebuffer canary and X11 diagnostic deliberately paint a transient
frame and then restore it before that marker, so the gate was sampling after
the useful frame had disappeared. `DesktopM3Operations` now supports an
explicit early capture marker for diagnostic profiles; ordinary desktop
profiles retain the final-marker capture.

The QEMU Bochs device is also created with an explicit `1280x1024` mode so
the guest and host capture dimensions are fixed. With the speculative
RISC-V framebuffer cache-policy change and the Bochs PCI decode special case
both reverted, the early-capture fbdev canary still passed:

| Gate | Result |
| --- | --- |
| `desktop_m4_fbdev_canary_gate` (ablation) | passed; 1280x1024, 3 sampled colors, 874,496/1,310,720 non-background pixels |
| `desktop_m4_x11_gate` | passed; 1280x1024, 86 sampled colors, 614,350/1,310,720 non-background pixels |
| ordinary `desktop_m4_gate` | still fails host PPM diversity; guest reports `distinct=3 non_background=2` |

These receipts establish that QEMU Bochs scanout, fb0 writes, and X11-to-fb0
submission work in a deterministic test. The remaining ordinary-desktop
failure is limited to the first visible GTK desktop frame (the guest sample
contains only two non-background pixels), so it must be debugged as an
application first-paint/readback issue before a physical desktop claim. No
physical boot was performed in this iteration.

## Ordinary desktop first-paint diagnosis

The ordinary M4 gate was then run with a bounded, read-only X11 diagnostic
captured after `DEBIAN_DESKTOP_M4_READY`. Xorg still reported a valid fbdev
screen at 1280x1024, and the dedicated override-redirect X11 paint gate passed
its three colour samples. The normal desktop clients, however, all remained
unmapped or had only their initial 10x10 placeholder geometry:

```
panel       1280x34+0+0  IsUnMapped
netsurf-gtk 10x10+10+10  IsUnMapped
lxpanel     10x10+10+10  IsUnMapped
pcmanfm     10x10+10+10  IsUnMapped
xterm       1x1+0+0      IsUnMapped (child 604x394, IsUnviewable)
```

Openbox was alive and had installed `_NET_SUPPORTING_WM_CHECK`; the Xorg log
contained no fatal error. This distinguishes the remaining ordinary-desktop
failure from framebuffer registration and from the scanout visibility fix:
the managed-client `MapRequest`/configure path is not reaching a visible
window, while a direct override-redirect client can paint into fbdev. The next
QEMU experiment will isolate the window-manager event path (no-WM and
matchbox controls) before any physical desktop boot is attempted. No desktop
workaround is accepted from this diagnostic alone.

A temporary no-window-manager control was also run against a clean copy of the
same root image. It removed Openbox from the session while leaving the Debian
clients and fbdev/Xorg contract unchanged (the image was modified only with
`debugfs`, then checked with `e2fsck -fn`). The guest still reached all M4
markers and the host capture remained below the screenshot diversity
threshold. This does not prove that the final fix is in the window manager,
but it rules out the simplest "Openbox alone blocks every first paint"
hypothesis. The temporary receipt is retained at
`target/qemu-m4-nowm-evidence/`; the modified image and gate wrapper were
deleted after the run.

Finally, the deterministic X11 paint helper was run once with only its
`override_redirect` attribute removed, so the same 960x640 client became a
normal window managed by Openbox. The gate stopped at
`DEBIAN_DESKTOP_M4_FAIL reason=x11-paint-test` before producing a matching
fb0 sample, while the override-redirect version continues to pass. This is a
minimal reproduction of the ordinary-client failure independent of GTK,
PCManFM, and NetSurf. Its serial receipt is retained at
`target/qemu-m4-managed-window-evidence/`; the modified image was deleted
afterward. The next implementation work should instrument the X11 map/configure
event path or the corresponding poll/epoll waits, rather than changing the
wallpaper or framebuffer cache policy.

## Epoll timing probe and settling-delay control

The ordinary M4 gate was run once with `asterinas.epoll_profile=1` and
`asterinas.epoll_entry_profile=1`. The host classifier reported a passing
1280x1024 screenshot (256 sampled colours and 253,913 non-background pixels),
but visual inspection showed only the xterm on a black background; the panel
and browser were still absent. The bounded profile reported no epoll errors;
the early calls were mostly zero-timeout polls with ordinary ready/empty
transitions. Thus epoll instrumentation changes timing enough to expose a
visible client, but it is not evidence that the desktop is accepted.

A separate temporary image changed the guest post-client settling sleep from
5 seconds to 30 seconds. That run produced no framebuffer or final-ready
marker within the 240-second gate budget. The fixed delay is therefore not a
safe solution; readiness must be tied to visible/map-state evidence with a
bounded per-client wait. The profile receipt was kept under
`target/qemu-m4-epoll-profile/`, and the negative settling control under
`target/qemu-m4-sleep30-evidence/`.

The QEMU ordered readiness predicate now requires bounded
`xdotool --onlyvisible` matches for PCManFM, LXPanel, xterm, and (when
enabled) NetSurf, in addition to the process and window-tree checks. A
temporary image containing this predicate did not reach the host completion
marker within the old 180-second budget, which is the expected red baseline
for the currently unmapped clients; its receipt is under
`target/qemu-m4-visible-gate-evidence/`. This gate change is intentionally
strict: a future QEMU pass must show the actual desktop clients, not only a
large terminal window.
