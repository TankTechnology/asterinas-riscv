## QEMU guest follow-up

The first guest-side `asterinas.gmac_diagnostic=phy` run failed with a stable
`readback-mismatch`: the model had HSP/SYSCRG windows but not the GPIO and
PINCTRL/RGMII windows touched first by `program_platform()`.  The QEMU model
now exposes only the required GPIO offsets (`0x00`, `0x04`) and RGMII offsets
(`0x290`, `0x294`) with resettable readback state.  The full qtest binary then
passed 11/11 tests, including `platform-aux-readback`.

The QEMU FDT also had an interrupt-parent mismatch: its PLIC was phandle 3
while the physical EIC7700 binding and Asterinas validation require phandle
16.  GMAC-enabled QEMU now reserves phandle 16 for the first PLIC and uses it
for all generated interrupt-parent properties.  The normal Asterinas guest
then reached `ASTERINAS_GMAC_SELECTED` and `ASTERINAS_GMAC_READY` without a
panic, and started the `eth0` poll thread.  This is a QEMU registration result,
not a physical-board result.

The QEMU-side PHY and descriptor gates are recorded in
`target/megrez-qemu-hardware-probe-20261006-gmac1-replay-v2/result.json`:
PHY status passes with no DMA/TX/RX side effects, and the fixed descriptor
loopback records one 96-byte TX/RX frame, zero TX/RX errors, and one IRQ.
No TCP/UDP traffic has been attempted, and the physical management channel
remains the prerequisite for any new board cycle.

The follow-up gated-port receipt is in
`target/eic7700-qemu/phase3c-20261007/result.json`.  It adds two reset
invariants: GMAC-1's shared reset register preserves GMAC-0's released bit,

expanded QTest suite passes 13/13.  With GMAC-1 initially clock-gated, both a
PHY-only guest and a normal registration guest pass; the latter reaches
`ASTERINAS_GMAC_DMA_CONTRACT`, `ASTERINAS_GMAC_SELECTED`, and
`ASTERINAS_GMAC_READY` and starts `eth0` polling without a panic.

A bounded guest self-network attempt was also run after registration.  The

## Physical first-read diagnosis

The earlier physical GMAC-1 receipts narrow the original hang to the first
MMIO access.  In `gmac-1-safe-20261006-r13` and `r15`, the transcript reaches
`ASTERINAS_PROBE_ATTEMPT device=gmac-1 offset=0x0000` but contains no matching
`ASTERINAS_PROBE_READ` marker before the cycle stops.  The normal GMAC/PHY
driver is not entered in this boot mode, so this is evidence of a blocked or
unavailable GMAC MMIO read while the clock/reset domain is not usable; it is
not evidence of a PHY negotiation failure.  The later `r16` run never loaded
the candidate and is classified as management-chain unavailable.

The corrected QEMU contract reproduces the safe boundary by returning
`0xffffffff` immediately for gated GMAC-1 reads, ignoring writes, and proving
256 repeated reads followed by a live GMAC-0 read.  No physical retry is
allowed until a fresh U-Boot prompt and nonce-bound RockOS recovery check are
observed.

## 2026-10-07 QEMU data-path correction

The QEMU external-netdev replay found a model-only descriptor-boundary bug.  The
model used `rx_cursor == rx_tail` as a global early-return condition, so after
the guest consumed and refilled one RX descriptor, a later TX descriptor was
silently held back.  The same condition also prevented the next external RX
packet even though its descriptor was still owned by DMA.  The model now keeps
TX progress independent of the RX tail and uses RX descriptor ownership for
external receive readiness.  Internal loopback still validates RX ownership.

The fix is commits `a375364`, `083686e`, and `8baab16` on `codex/eic7700-gmac-phase3`.
`083686e` flushes queued NetClient packets after a successful RX completion, and `8baab16` flushes again at the guest RX-tail write boundary so a frame queued before refill cannot remain stuck.
The expanded QTest suite passes 15/15.  The regression test publishes two TX descriptors, consumes
one external RX frame, and verifies that the second TX frame is delivered, its
OWN bit is cleared, the QOM counters are `tx_packets=2`, `rx_packets=2`, and
DMA status does not gain `DMA_STATUS_RX_BUFFER_UNAVAILABLE`.  The final TAP receipt is `target/eic7700-qemu/phase3c-20261007/qtest-tx-after-rx/qtest-final5.tap` with SHA-256 `d0b16642c5be7ceeced087e2164ed14568e5505f0739742a035d4f8f60842075`; it contains 15/15 passing tests, including the queued-RX-frame refill regression.  The same test against the pre-fix binary fails at the RX descriptor assertion (`0xc1000000` still OWN) and is archived as `before-rx-tail-flush-failing.tap` with SHA-256 `c123b7477c18ea4197c6a2ba6ac92f2411f53f3efdfebd03e755f1fb348bc961`.

A current-kernel guest replay with `-cpu rv64,svpbmt=true` then completed four
TCP connections.  The ACK-paced responder delivered the four configured HTTP
payloads (16 KiB, 64 KiB, 1 MiB, and 1 MiB), for `completed_bytes=2179072`,
with 1,817 data segments and four FIN packets.  The guest emitted four
`ASTERINAS_GMAC_TCP_PROBE_PROGRESS` markers followed by
`ASTERINAS_GMAC_TCP_PROBE_READY`; no `ASTERINAS_GMAC_TCP_PROBE_FAIL` marker
appeared.  Sampled GMAC diagnostics reported zero TX/RX errors and zero RX
buffer-unavailable events.  The prior partial result had two causes: the
runner wrote the complete response in one blocking socket operation, and the
model did not flush an already queued frame when the guest later wrote RX
TAIL.  The ACK-paced runner and `8baab16` address both boundaries.

Evidence is in `target/eic7700-qemu/phase3c-20261007/guest-tcp-ack-paced/`:
