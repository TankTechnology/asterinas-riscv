## Interpretation

- The binary and profile are healthy (L0), and virgl/EGL is healthy (L1).
- Headless Firefox starts but does not reach a WebRender/compositor log line
  or a screenshot within 30 s.  This is the local fact requested for r141.
- The 30 s bound cannot distinguish a permanent hang from TCG slowness beyond
  30 s.  Per the ladder discipline, the ladder stops at L2 rather than
  repeating the full scene chain.
- r24 is retained and remains complementary: with WebRender explicitly
  disabled, the full-chain probe still times out at the same
  `PCompositorBridgeChild::SendResume()` synchronous IPC.  The live stack r22
  (same kernel) resolves to
  `nsWindow::OnMap → ConfigureCompositor → ResumeCompositorImpl →
  SendResume → MessageChannel::Send → WaitForSyncNotify → pthread_cond_wait`.
  Thus the startup block is the compositor Resume handshake, not WebRender
  shader/compositor initialization itself.

## L2b follow-up (120 s bound)

A second ladder run (`/mnt/mydisk/qemu-firefox-e3-ladder-r141f`, rootfs
`dc8ad012…`) repeated the same headless command with a 120 s bound:

| Fact | Result |
|---|---|
| process exit | rc=0, 93458.4 ms, no timeout |
| screenshot | exists, 20146 bytes, sha256 `7a6fa6d369ab4fb4872652b4ebcb287889eaff6c9e4d1bca608699786e8c1136` |
| WebRender init | browser log: `WebRender - OpenGL version new 3.2`, `Renderer: Software WebRender`, `is_software: true` |
| renderer | **Software WebRender**, not virgl (glxtest still reports virgl/EGL) |

So the 30 s L2 bound was below the headless cold-start envelope.  WebRender
can initialise in this guest, but it selects software WebRender and needs
about 93.5 s.  This answers the r141 WebRender-initialization question and
does **not** satisfy E3's virgl renderer requirement.

The full-chain NewSession stall is separate: r22's live stack resolves to
`nsWindow::OnMap → ConfigureCompositor → ResumeCompositorImpl →
PCompositorBridgeChild::SendResume → MessageChannel::WaitForSyncNotify`, and
r24 (WebRender disabled) still times out at that same compositor Resume sync
IPC.

Structured receipt: `docs/porting/diagnostics/2026-10-21-e3-ladder-L2b-r141.json`.

## Next boundary

The next bounded step is the compositor Resume sync IPC itself: determine
whether the compositor thread is spinning or blocked, and whether a
non-headless configuration (software compositor / GPU-process off) lets
`SendResume` reply.  Only after NewSession returns is an L5/L6 scene run or a
physical-board run justified.  No full scene run is justified by this receipt.
