# Network interface metadata for native LMBench on RISC-V QEMU

Committed serial logs have carriage returns and terminal trailing whitespace
removed; the linked hashes identify these normalized copies.

The pinned native LMBench `make results` run already completed 109/109 selected
measurement groups on the earlier kernel. Its setup still printed warnings from
the original `netstat -i` and `ifconfig -a` helpers. Adding `/proc/net/dev`
removed the missing-file warning, but exposed a second compatibility gap:
`netstat -i` exited 1 because the socket interface-information ioctl returned
`ENOTTY`. [The original-helper baseline](2026-09-24-ifreq-nettools-baseline.log)
records `eth0: error fetching interface information: Inappropriate ioctl for
device`; its SHA256 is
`1ffc656abc79eae576ad93e7f6d8b1a18faf220f7b92a1675906f84bd1f260ca`.

The original [net-tools interface lookup](https://github.com/ecki/net-tools/blob/master/lib/interface.c)
requests interface flags, hardware address, MTU, IPv4 address, broadcast
address and netmask. The kernel now answers those read-only `SIOCGIF*` queries,
plus interface index, from the caller's network namespace. An absent interface
returns `ENODEV`; an invalid user pointer returns `EFAULT`. This also allows
the same original `ifconfig -a` binary to display the interface metadata.
Other socket ioctls remain outside this change.

The first implementation reported `eth0` MTU as 1514 because the smoltcp
Ethernet device capability counts the 14-byte header, while the Linux interface
MTU does not. The exported interface MTU now excludes that header. When a
virtio device negotiates its MTU, the driver converts the supplied IP MTU back
to smoltcp's frame-size convention. A loopback interface without the BROADCAST
flag now returns a zero broadcast address. The pinned
[smoltcp capability contract](https://github.com/asterinas/smoltcp/blob/r_2024-11-08_f07e5b5/src/phy/mod.rs)
and the [Virtio 1.1 network-device specification](https://docs.oasis-open.org/virtio/virtio/v1.1/virtio-v1.1.html)
define those two MTU conventions.

## Focused validation

The `AUTO_TEST=ifreq` gate boots a four-CPU RISC-V `virt` QEMU with a virtio
network device. It checks loopback and Ethernet flags, addresses, netmasks,
broadcast addresses, hardware types, MTUs and indices. It also checks missing
interfaces, a bad userspace pointer, and isolation after `unshare(CLONE_NEWNET)`.
The test failed on the previous kernel at its first flags ioctl; the
[baseline transcript](2026-09-24-ifreq-baseline.log) has SHA256
`f7cb04f710fa41734910957555d398e7a3f83eadd758c856ee2cc70067dab37e`.
It passed on the new kernel using:

```sh
make run_kernel AUTO_TEST=ifreq TARGET_ARCH=riscv64 SMP=4 FEATURES=riscv_sv39_mode RELEASE=1
```

The [passing QEMU transcript](2026-09-24-ifreq-qemu.log) has SHA256
`e8c858a4e75b5116ce5bdc9e72622529a15bac19876f6e4d7d40bdd6e837b7c2`.
The production kernel image SHA256 was
`e8917b430210f2b6b85e5d747b3f5162e8c3ceb01cd4f0a692cfd5c6da18a91c`.

The original net-tools binaries then ran inside the Debian RISC-V QEMU guest
on the kernel with the `ifreq` and MTU changes. `netstat -i` and `ifconfig -a`
both exited zero.
They displayed `eth0` with MTU 1500, IPv4 `10.0.2.15/24`, broadcast
`10.0.2.255`, MAC `52:54:00:12:34:56`, and packet counters. The
[helper transcript](2026-09-24-ifreq-nettools-ifreq-mtu.log) has SHA256
`f4098e895a54f613c11dac0fd384ceb10a2448c0d4220308f37856b30c9a406b`.
The later loopback-broadcast guard was covered by the passing focused QEMU
gate on the final image; the helper transcript was captured immediately before
that guard was added.
The separate RISC-V `AUTO_TEST=ifconf` gate also passed all 10 cases after the
shared IPv4 sockaddr helper was refactored. Its
[QEMU transcript](2026-09-24-ifconf-followup-qemu.log) has SHA256
`1bc3d689cf1a6337940f7fb14a2eb1f98abcedfd55aaf0184efecd80d3cddb8f`.

## Native driver header mismatch

The first native ALL run on the final kernel image emitted all 109 expected
measurement groups, including RPC/UDP and RPC/TCP, and `make` itself exited
zero after 600.637 seconds. Independent auditing correctly rejected the run:
the original LMBench driver passed `Kernel` and `Iface`, the two header labels
from modern `netstat -i`, to `ifconfig` as if they were interface names.
The resulting `Device not found` errors are in the
[raw native result](2026-09-24-ifreq-native-baseline-results.txt) (SHA256
`250776a1aa0c724a8ea78ec85fb77270c18b336f71150a035de855bab48f2743`)
and [audit report](2026-09-24-ifreq-native-baseline-report.json) (SHA256
`82be00777310843d17d33a49d58d38105212654fb86c0b45e2fb765f531926a6`).
The original `netstat` and `ifconfig` binaries had passed the separate QEMU
helper test, so this failure was in LMBench's header parsing, not interface
lookup. The native script already skips a historical `*ame` column heading;
the package adaptation also skips the two modern headings. It retains the
original `netstat -i`, `ifconfig`, benchmark binaries, and measurement commands.
The package still records the original script hashes and declares this extra
adaptation. A shell regression reproduces the former spurious invocations and
asserts that only `eth0` is queried after adaptation. The two packages have
identical SHA256 maps for all 58 packaged ELF binaries and identical hashes
for the original upstream scripts. The adapted package SHA256 is
`e65c52261a1483c12196840a7d15f70ea272bad7d0dc66ad3d10b72552961087`.

## Final native ALL qualification

The adapted package ran the same `cd /opt/lmbench/src && make results` command
on the same production kernel image. QEMU boot ID was
`fcf07b47-2b5d-4771-b4ae-17770cc41be6`. The native driver returned zero
after 591.668 seconds. Independent auditing found **109/109** expected
measurement groups, no missing groups, no errors and no metadata warnings.
The [final report](2026-09-24-ifreq-native-pass-report.json) has SHA256
`d2d23d4586790f54ec34bdbf589e8710b2c0174b6b92d0301143d5bbe9bdb20b`;
the [raw result](2026-09-24-ifreq-native-pass-results.txt) has SHA256
`01a76cb3598f907020cf168733dfc9db9b2999068f76aff02c8f4c3226761a78`;
and the [native configuration](2026-09-24-ifreq-native-pass-config.txt) has
SHA256 `2a227658b684f7564c7ea00b2dd27dfe8bc36424d60ad5c474f5f358fb9c3cc3`.
The [full host serial transcript](2026-09-24-ifreq-native-pass-serial.log) SHA256 is
`abf775dc267e4c436548473c5e2814686bdfbaa8cae391b9eaf210c07814496a`.
The passing raw result retains both `netstat` headings but contains `ifconfig`
details only for `eth0` and `lo`; no fake `Kernel` or `Iface` queries remain.
The report's binary-hash map exactly matches the prior rejected run.

This is a QEMU TCG compatibility result for the configured native ALL suite,
not a performance score or a claim about raw disks, remote hosts, every
standalone LMBench executable, or physical hardware. `lo` still reports an
MTU of 65535 under the current network-device convention; it does not prevent
the selected native suite or helper commands from completing.
