# clone/fork 成本实测：56.5 ms/次的说法不再成立（当前 2.4 ms/次，总计 61 ms）

日期：2026-10-26
内核基线：`a966812e2`
本轮：纯测量，**未改内核代码**

## 0. 结论（与任务书前提不一致，如实报告）

1. **当前 Firefox 启动里的 clone 单次是 2.36 ms，不是 56.5 ms**：
   `clone`(56) 26 次 / 61.3 ms，`clone3`(435) 6 次 / 2.2 ms。
   上一轮 `56.5 ms/次` 来自 postmap 探针那一轮——那轮**同时开着逐 syscall 计时**（每次 syscall 都有 rdtsc）
   且并行跑 5 个 `/proc` 采样循环，属于抬高后的数字。
2. 于是验收目标里的两条都不成立：
   - `<20 ms/次`：**已经满足**（2.36 ms）；
   - 「冷启动降 ≥300 ms」：clone **总共只有 61 ms**，即使归零也不够 300 ms。
3. fork 成本的两个驱动因子都量到了：
   - **驻留页**：约 **1.7 µs/页**（1k→5 ms、8k→17 ms、32k→55 ms、64k→110 ms，线性）；
   - **VmSize**：同等 RSS 下 64→256→512 GiB 分别是 44→53→59 ms（弱相关但真实）。
4. 因此 **任务 B 没有做**：没有 56.5 ms 可砍，且时间盒不足以安全改 `fork_from` 并跑完矩阵。

## 1. 任务 A 数据

### 1.1 fork 成本 vs 驻留页（2 GiB 映射）

| 触碰页数 | RSS | 每次 fork |
|---|---|---|
| 1 024 | 4 MB | **5 ms** |
| 8 192 | 32 MB | 17 ms |
| 32 768 | 128 MB | 55 ms |
| 65 536 | 256 MB | 110 ms |

≈ **1.7 µs/页**，与 `cow_copy_pt` 逐页处理（父页保护 + 子页映射）的实现一致。

### 1.2 fork 成本 vs VmSize（固定 1k 页 ≈4 MB RSS）

| VmSize | 每次 fork（5 次均值） |
|---|---|
| 2 GiB | 5 ms |
| 4 GiB | 46 ms（**样本噪声**：9 次复测为 **10 ms**） |
| 64 GiB（RSS 88 MB） | 44 ms |
| 256 GiB（RSS 88 MB） | 53 ms |
| 512 GiB（RSS 88 MB） | 59 ms |

Firefox 父进程 **VmSize 466 423 808 kB（≈445 GiB）**、**VmRSS ≈90 MB**，
但它的 clone 平均只有 **2.36 ms**——与「RSS≈88 MB 的合成进程需要 44–59 ms」**相差 20 倍**。

### 1.4 这个矛盾的两种解释（未进一步区分）

1. **Firefox 的 fork 发生在 RSS 很小时**：表里 1 s 时 RSS 已 59 MB，但内容进程可能更早 fork，
   那时 RSS 只有几十 MB → 按 1.7 µs/页算 2.36 ms ≈ 1 400 页 ≈ 5.5 MB，与「启动最初几毫秒」吻合。
2. **Firefox 的映射以文件页为主**，而我的合成用例全是匿名页；若文件映射在 fork 里走的是另一条路径
   （例如只读文件页不逐页 COW），成本会显著不同。**这一点本轮没有测**，需要专门的
   「匿名 vs 只读文件映射」对照实验来判定。

## 2. 任务 B：未做（前提不成立 + 时间不足）

候选 B1（只读页表子树共享）之所以有价值的前提是「fork 里大量工作是只读页的 COW 复制」，
而 1.4 的第 2 条尚未验证；在没有该数据前改 `fork_from` 属于猜测。

若下一轮要做，建议顺序：
1. 先跑 1.4 的对照实验（匿名 vs 只读文件映射，同 RSS），确认文件页是否被逐页 COW；
2. 再按上面第 2 条结论决定是否做「只读子树共享」；
3. Firefox 侧的真实指标应以 **不含逐 syscall 计时** 的轮次为准（本轮 2.36 ms）。
