# Asterinas 组件化测试工程方案

状态：设计提案，未实施、未编译验证。
日期：2026-09-10。
跟踪：[TankTechnology/asterinas-riscv #138](https://github.com/TankTechnology/asterinas-riscv/issues/138)。
首阶段任务：[M0 只读验证计划](../plans/2026-09-10-component-testing-m0.md)。

## 1. 决策摘要

复用 Asterinas 的真实组件源码，为测试提供可选择的运行环境。
不复制一套组件实现，不维护 `asterinas-lite`，不要求生产内核先改成微内核。
短期交付是缩短开发反馈周期的工程设施，不以论文创新成立为前提。

最终希望开发者能够选择一个组件组合，运行边界条件与错误处理测试，
在失败时得到源码身份、触发操作、关键事件和可重复的回归用例。
组件运行在宿主普通进程中；无法合理抽取的行为继续在内核测试或真机中验证。

当前仅形成方案。
本文件及 #138 不授权修改其他 agent 的工作区、启动构建、占用板卡或改动 GitHub 上的其他任务。
本次只新增方案文档，不提交、不切分支、不改变现有开发代码。
后续实施必须先取得实施授权，在独立工作区进行，并逐阶段评审公共接口改动。

## 2. 范围与非目标

覆盖方向包括网络、文件系统、系统调用（syscall）、IPC 和设备驱动。
并发错误只是其中一类；错误码、数据一致性、权限、资源回滚等同样重要。

首个原型只解决一个真实源码运行边界，以及一组可重复的正负控制。
第二阶段必须引入不同组件的非并发案例，检验底座能否复用。
不以一次接入全部子系统作为首个版本的完成条件。

首版不提供以下能力：

- 完整 OSTD 宿主移植、真实调度器和内核栈切换的验证。
- 全部原子操作的确定性调度或弱内存行为穷尽探索。
- 完整 CPU、IOMMU、缓存一致性或某一 SoC 的仿真。
- 运行桌面、发行版或通用用户态应用。
- 对组件通过测试后不会再出现 bug 的证明。
- 自动抽取任意内核模块、自动推导任意 API 的正确语义。

## 3. 已有证据与设计假设

此次源码调查固定在 `c20bfac0f254defff82f72ab4c6eef2fb1af9fcd`，
而不是把正在变化的工作区或远端 `main` 当作固定事实。
实施时需重新选择集成基线；历史故障的版本身份不得随之改变。

| 项目 | 已核对的证据 | 尚不能据此声称的结论 |
|---|---|---|
| SCM 引用图 | 实际依赖主要是容器、引用计数、原子数值和锁；没有直接使用完整 socket 实现 | 已经能够宿主编译 |
| 锁与等待队列 | Mutex 慢路径经过 WaitQueue、Task 身份及 park/unpark | 替换 Task 后保留了真实调度器行为 |

## 4. 方案选择

| 路线 | 优点 | 代价 | 决策 |
|---|---|---|---|
| 重写精简内核 | 可以自由设计测试接口 | 两份实现分叉，测试与生产逻辑不一致 | 不采用 |
| 真实源码 + 可组合测试底座 | 可保留目标实现，控制输入和环境，快速迭代 | 需要建立适配边界并校验语义 | 主路线，先做小原型 |
| 精简 QEMU 内核批量测试 | 保留更多真实依赖，减少抽取工作 | 启动、状态控制和调试仍有成本 | 保留为对照与退路 |

源码复用不要求两个构建产生相同机器码。
宿主构建可能是 x86-64，生产目标可能是 RISC-V。
平台指令、布局和内存排序差异必须单独记录，不能用宿主通过替代架构验证。

## 5. 最终形态

```text
                  同一份 Asterinas 组件源码
                             |
              +--------------+---------------+
              |                              |
         正式内核构建                     组件测试构建
              |                              |
       真实 OSTD / 设备               测试运行底座 + 环境后端
              |                              |
       QEMU / 实际开发板               普通进程中的测试组合
```

“组件”可以是多个模块形成的组合，而不是强制等于一个 Rust crate。
例如 syscall + 文件表 + 文件系统，或者 socket 层 + 协议栈 + 虚拟链路。
只替换与目标性质无关或有明确适配规则的依赖。
不能为了缩小测试规模而替换掉目标错误所在的锁、缓存或生命周期实现。

### 5.1 新增内容及拟议位置

以下是后续原型的职责划分，不表示这些目录、接口或命令已经存在。
首次实施在独立工作区内进行，不立刻修改根 workspace、Makefile 或 CI。

| 拟议位置 | 职责 |
|---|---|
| `tools/component-test/README.md` | 使用方法、支持范围、权限要求和结果解释 |
| `tools/component-test/runner/` | 选择案例，启动子进程，收集结果和管理预算 |
| `tools/component-test/cases/` | 真实组件组合、输入序列和测试判据 |
| `tools/component-test/manifests/` | 源码身份、组件依赖及后端配置 |
| `tools/component-test/repro/` | 小型、审阅过的回归输入；不放大型原始日志 |
| `ostd/host-test/` | 拟议的测试专用 OSTD 适配边界；位置与安全设计先评审 |

真实源码通过显式路径依赖或生成的源码装配入口复用。
若需要生成源文件副本，副本必须是可再生的构建产物，逐文件验证源哈希，禁止人工修改。
普通 wrapper 不复制待测算法；导入、可见性、cfg 调整与行为修改分别审计。
阶段一不把原始 `#[cfg(ktest)]` 全量打开，以免连带引入真实内核线程设施。

运行底座中必须复用的 unsafe 代码仍处于 OSTD 的受审计边界。
不向 `kernel/` 添加 unsafe，也不借测试 wrapper 绕过 safe kernel 的边界。
以模拟状态实现的 guard 只适用于已审计的测试组合，
不得被当作真实关中断/禁抢占保证，接入依赖物理 CPU 行为的任意 OSTD 代码。

### 5.2 逐步建立的后端

| 后端 | 提供什么 | 不自动覆盖什么 |
|---|---|---|
| 任务与逻辑 CPU | 当前任务身份、等待/唤醒、局部状态 | 真实调度策略、迁移、内核栈 |
| 时间与事件 | 可推进的时间、可选择的事件边界 | 全指令确定性、真实硬件时序 |
| 用户内存 | 地址范围、权限及受控访问失败 | 实际页表、TLB、硬件 page fault |
| 报文链路 | 报文输入、丢失、乱序和模拟对端 | 网卡 DMA、PHY、电气链路 |
| 存储 | 块读写、容量和显式失败 | 未建模的持久化、掉电和写回排序 |
| 设备 | 指定设备子协议中的寄存器和完成事件 | 任意设备或整块 SoC 的真实性 |

前三类也不要求在首个 pilot 全部实现。
后端需要模拟的行为由测试目标决定，不能仅按“接口能返回结果”判断可用。

## 6. 首个 pilot：SCM 引用关系释放

SCM_RIGHTS 是 UNIX socket 传递文件描述符的机制。
候选图结构追踪相关引用关系；Drop 是 Rust 对象释放时执行的析构操作。

历史版本固定为：

- 修复前：`d93cd066d7afdb1c6531b52ba6bfbb223ec4e4f0`。
- 修复后：`e20f2832bec51af6b6f501811247d67ae052d190`。

修复将图的全局锁从 Mutex 改为 SpinLock。
各版本源码与依赖均来自对应版本；同一套 adapter、案例及判据用于两边。
如需统一依赖版本，先证明所选依赖在比较中不变，并明确记录这一实验变体。

### 6.1 保留与替换的边界

保留图操作、引用计数、析构、锁和等待队列的真实实现，以及原子上下文检查规则。
替换 Task 身份、park/unpark 和每逻辑 CPU 的状态来源。
不保留真实 `switch_to_task`；它牵引 RCU、内核栈和架构上下文切换。

首次采用两个宿主线程承载两个固定逻辑 CPU，不支持任务迁移。
不能用单线程执行器运行没有让出点的真实自旋循环，否则其他 CPU 无法释放锁。
也不能将禁抢占建模成冻结所有逻辑 CPU。

适配层仅在经过唤醒检查、实际需要切换/阻塞的路径上应用睡眠约束。
预先唤醒或无争用快速返回不能被 blanket assert 错误拒绝。
需要明确一个可运行的替代任务/idle 上下文来对应目标切换条件，
不能把每次调用 park 都等同于真实内核一定发生上下文切换。

### 6.2 必须通过的场景

| 场景 | 必须观察到的行为 |
|---|---|
| 旧版、无争用、禁抢占 Drop | 快路径完成，不制造睡眠错误 |
| 旧版、有争用、禁抢占 Drop | 真实锁/等待队列慢路径进入切换请求，触发预定义原子上下文判据 |
| 旧版、有争用、普通上下文 | 能等待、唤醒并完成 |
| 新版、有争用、禁抢占 Drop | 另一逻辑 CPU 释放锁后完成，不进入目标睡眠路径 |
| 等待前唤醒 | 不丢失已到达的唤醒，不产生错误阻塞判定 |

争用案例必须记录锁所有者、尝试获取的时刻及释放次序。
外部测试控制器暂停某逻辑 CPU 不属于组件主动睡眠，不能作为 atomic-context 错误证据。
初始化在进入故障场景前完成；bootstrap 豁免应结束。
同一进程中的 Once 和全局状态暂不重置，每次试验使用新子进程。

原型验收每个场景至少完成 100 次满足前置条件的有效运行，总尝试数初始上限为 200 次。
记录全部尝试、结果及触发条件；在开始试验前固定每次运行的超时和资源预算。
这是工程稳定性门槛，不是统计证明或穷尽覆盖。
未形成争用的运行、启动失败、无关 panic 和普通超时单独分类，不能计为正确触发。
总尝试预算耗尽但有效运行不足时，不通过该场景验收；不得删除失败记录后重算分母。
任一未解释的结果均阻止该场景被标为稳定通过。
新增的宿主结果在建立对应内核证据前，称为“历史缺陷宿主校准”，不称为新发现的内核 bug。

### 6.3 特别风险

- 宿主 allocator 的行为不能证明内核分配在原子上下文中安全。
- 宿主 panic 展开可能再次执行析构；首版优先记录后终止单次子进程，避免继续使用损坏状态。
- 真实原子操作和自旋指令不会自动被事件控制器拦截；首版只控制已声明的边界。
- 简化 park/unpark 不覆盖真实 runqueue 的全部 lost-wakeup 和调度问题。
- 修复提交里的类型断言没有动态构造旧版 Mutex 争用，不能作为旧版已复现的证据。

## 7. 从回归用例走向主动发现错误

能力检查只是运行前的条件核对。
实际发现错误需要操作生成、环境扰动、独立判据和失败缩减。

工作流为：

1. 从已有回归和 API 规则获得种子操作序列。
2. 改变参数、操作顺序和长度；在已声明边界改变资源失败、时间或外部事件。
3. 执行真实组件，检查返回值、数据内容、权限、资源账本和生命周期规则。
4. 保留触发同一判据的输入与事件次序，缩减无关操作和数值。
5. 重复组件复现，再将可映射场景转换为内核测试，确认或保留未决。

首版采用有界枚举和固定场景，不自研通用 fuzzer。
出现明显收益后再引入覆盖引导；只有经过插桩的部分才能报告其覆盖率。
设备事件需遵守所选协议；不可能的设备行为与正常设备条件下的错误分开记录。

非并发示例：对支持扩展的普通文件，成功执行写入、缩短、再扩展后，
新扩展区域应读到零；测试在页边界附近变化长度，检查旧数据是否重新可见。
判据来自接口语义，不是照抄待测函数的实现。
此例是候选测试性质，不代表已经确认仓库存在相应 bug。[参考 5]

M2 优先调查真实 Ramfs/PageCache/文件操作组合，
但若依赖代价过大，应选择其他有证据的非并发组件案例。
不得通过重写一个假 Ramfs 来满足跨子系统验收。

## 8. 结果、复现与隔离

每次执行至少保存以下身份和事实：

- 案例 ID、源码完整提交、实际编译源文件哈希、依赖锁文件和适配层版本。
- Rust 工具链、宿主目标、生产对照目标、组件组合及后端配置。
- 操作输入、seed、逻辑 CPU 数、事件约束与实际观测事件。
- 判据 ID、触发点、子进程退出状态、超时/资源预算和各阶段耗时。
- 重复尝试次数、每次结果、缩减前后输入，以及内核对照证据位置。

原始状态分为：`PASS`、`VIOLATION`、`UNSUPPORTED`、`INFRA_ERROR`、`INCONCLUSIVE`。
这些是拟议结果格式，不是现有工具已经提供的接口。
历史错误版本的预期 `VIOLATION` 可以令回归案例验收成功，
但原始结果不能被改写成组件无错误的 `PASS`。
超时若没有满足明确的进展假设，记为 `INCONCLUSIVE`，不自动等于死锁。

故障确认另记为：宿主校准、内核确认、适配器缺陷、模型不足或未决。
同一个根因的多个输入去重；历史回归、新 bug、合成变异分开统计。
相同 seed 只代表输入选择可重现，不自动保证操作系统线程交错可重现。

构建沿用项目规定的持久化开发容器和固定工具链。
执行待测程序则必须具备无特权身份、资源限制与禁止真实设备访问的独立隔离条件。
开发容器可能带有较高权限和宿主挂载，不能直接将“在 Docker 中运行”等同于安全沙箱。
首版不访问真实网络、设备节点或生产磁盘；不配置 TAP，不授予原始 I/O 权限。
若隔离前提不满足，先报告基础设施问题，不运行错误注入场景。

## 9. 阶段交付与验收

| 阶段 | 交付 | 进入下一阶段的条件 |
|---|---|---|
| M0：只读调查 | 案例/依赖清单、源码身份、已存在测试盘点、原型决策 | 明确首个边界与第二案例候选，列清不支持的行为 |
| M1：宿主 pilot | 真实源码构建、最小底座、SCM 正负控制、隔离结果记录 | 场景稳定，差异有解释，没有针对 old/new 的专用 adapter |
| M2：跨组件与主动测试 | 独立非并发案例、操作/故障生成、判据与缩减 | 公共底座可复用，得到可重复的错误或正常边界行为；不以必须发现未知 bug 验收 |
| M3：日常回归 | 支持案例的内核对照、使用入口、报告及经过评审的 CI 接入 | 身份可追溯、结果不混淆、反馈成本可衡量且有实际收益 |

M0 的详细任务单独列出，避免将尚未验证的接口写成可直接实现的代码。
M1 的代码级实施计划在 M0 决策和用户授权后另行形成。
M2 各子系统按独立小计划接入，不一次性冻结全部后端设计。

用户入口目标是“一条命令选择案例并得到结果”，但目前没有新增命令。
现有 `make test`、`make ktest` 不能被误描述为已具有本方案的组件装配功能。

## 10. 成本预算与效果评估

以下为工程估算，不是已经测得的代码量或交付承诺。
按新增物理行粗估，含注释和测试，不含复用源代码、生成代码、第三方依赖及文档。
每行是累计规模，不相加。

| 阶段 | 底座与适配层 | 测试与脚本 | 累计新增 |
|---|---:|---:|---:|
| 首个原型 | 1,000–3,000 | 1,000–2,000 | 2,000–5,000 |
| 两三类组件可日常使用 | 3,000–7,000 | 3,000–8,000 | 6,000–15,000 |
| 多后端及部分驱动扩展 | 6,000–15,000 | 8,000–20,000 | 14,000–35,000 |

复杂设备模型和完整 OSTD 宿主移植不包含在上述预算中。
生产代码改动另报文件数、行为变化和审查成本，不能被总代码量掩盖。
单个熟悉 Asterinas 的开发者，首个原型按数周规划，实用工具按数月规划。
M0 后依据实际依赖修订，不把这个粗估作为期限保证。

首个 pilot 接近 5,000 行仍无法完成时，应复审边界而不是自动扩容。
记录人时和维护成本，不用行数替代工作量。

效果对照必须使用同一组件、同一版本、相同工作负载与合理的已有测试配置：

- 分开报告增量构建、初始化、单次执行、批量执行及失败复现的成本。
- QEMU 对照包含预构建、一次启动批量运行的情况，不能默认每个用例重新启动。
- 记录相同预算内的有效场景、已确认独立 bug、误报、未决和不支持案例。
- 新 bug 的数量是研究结果，不是基础设施必然产生的交付承诺。
- 若比较历史缺陷检出比例，必须事先列出完整入选清单及无法复现的原因。
- 不直接用 NetBSD 与 Asterinas 的运行时间差异推断方案优劣。

## 11. 已有工作与研究探索的边界

rump 提供真实内核组件的用户态执行与可组合环境，值得直接借鉴。[参考 1、2]
`rumpuser` 已规定运行上下文、I/O 完成和同步等行为规则，
不能把“环境接口有契约”本身说成新的贡献。[参考 3]
CONVEROS 已在 Asterinas 上研究模型与真实并发实现的一致性。[参考 4]

工程线独立成立：改善组件开发与回归体验。
研究候选是利用环境规则指导主动场景探索、错误检测和复现，
在相同成本下发现并确认更多有价值的真实缺陷。
它仍需对照内核模糊测试、模型驱动测试、故障注入及相关程序分析工作。
不承诺先验新颖性，也不为论文而人为制造现有方案的弱基线。

## 12. 停止、降级与协调规则

出现以下情形时，暂停相应组件的宿主化，复审边界或转向精简 QEMU 测试：

- 必须重写待测算法，或每个 bug 都需要专用的通用底座分支。
- old/new 使用不同的错误判据或语义适配，无法进行可解释比较。
- 仅靠更强的人为断言才能复现历史错误。
- 第二案例需要重复搭建第一套运行底座，未体现可复用收益。
- 模型行为与真实依赖无法对应，且对目标错误有实质影响。
- 需要真实栈切换、页表或设备才能回答目标问题，却仍强行声称宿主覆盖。
- 接入和演化成本持续高于已有测试路线收益。

已有网络问题可作为边界调查材料：
[#132](https://github.com/TankTechnology/asterinas-riscv/issues/132) 涉及用户页访问与网络锁，
[#94](https://github.com/TankTechnology/asterinas-riscv/issues/94) 记录了离线检查通过但真机仍失败。
本方案没有独立复现它们，也不预设 #94 的根因。

后续每个阶段报告四项：本阶段复用了什么、新增了什么、验证了什么、还不能说明什么。
跨 agent 的共享接口、根构建和 CI 变更拆成独立评审；真机验证另行批准。
